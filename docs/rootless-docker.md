# Rootless Docker

Omarchy runs ordinary development containers in a per-user rootless Docker daemon while retaining a separate rootful Docker daemon for the Windows VM. This keeps the Docker CLI, Compose, Buildx, and image format unchanged while removing the root-equivalent `docker` group from the development path.

## Runtime boundary

The user daemon is `docker.service` from `docker-rootless-extras`. It listens on `$XDG_RUNTIME_DIR/docker.sock`, stores engine data below `~/.local/share/docker`, and reads daemon configuration from `~/.config/docker/daemon.json`. `default/systemd/user-environment-generators/60-omarchy-rootless-docker` and `default/bash/env-bootstrap` export `DOCKER_HOST` only after `~/.local/state/omarchy/rootless-docker/enabled` exists.

The system daemon remains socket-activated for `omarchy-windows-vm`. Its vendor drop-in makes `/run/docker.sock` root-owned with mode `0600`, and migration verifies both the effective systemd socket properties and the daemon process's open sockets before and after connection revocation. A later administrator override, custom Unix listener, or TCP listener stops automatic migration. The verifier connects through dockerd's `/proc` mount namespace and checks the Unix peer before that exact endpoint is exported for every source command. The Windows command derives the same namespace-bound endpoint after authenticating with `sudo` or `pkexec`; user mounts, Docker settings, and `DOCKER_HOST` cannot redirect the privileged VM command.

## Fresh installs and additional users

The root setup allocates each account a nonoverlapping subordinate UID and GID range of at least 65,536 IDs and writes `/var/lib/omarchy/rootless-docker/enabled`. Existing ranges and new allocations must also exclude every UID or GID currently assigned through NSS, including root and high-numbered directory-service identities. The resolved account's own UID, primary GID, and supplementary groups remain reserved even when its NSS provider disables enumeration. The allocator also resolves every username or numeric owner found in either subordinate-ID file, so an owner visible in only one file still constrains both UID and GID allocation. The locked allocator rereads both files and NSS identities after `usermod` before accepting the result. User finalization creates the private marker and daemon config, then first-run setup enables the rootless service only for that initialized account. Existing accounts follow the same order during migration; no global user-unit symlink can start Docker for another account before its subordinate IDs and daemon config exist.

The migration's machine-wide enabled marker is written only after the shared rootful inventory has migrated and `/run/docker.sock` has been restricted. When another account later runs the per-user migration, it initializes that account's rootless daemon and returns before inspecting the retained rootful recovery store.

## Existing-install migration

`migrations/1789164756.sh` installs the rootless runtime, allocates subordinate IDs, starts an inactive user daemon, and proves the daemon with that account's configuration before migrating the shared rootful store. An already active rootless daemon is validated in place and never restarted, so a custom-policy rejection or later destination collision leaves its existing workloads running. The migration then restricts and verifies the old API socket, secures any current account's Windows definition through the verified daemon namespace, and preflights every rootful container. The rootful daemon configuration is opened beneath `/proc/$pid/root` without following symlinks and must be a root-owned, non-writable regular file below trusted parents. It must predate the running process, and the active command line must select the packaged executable and standard config path; the same checks run again immediately before and after the mandatory daemon restart. The rootless daemon configuration is opened without following symlinks through its live dockerd mount namespace, must remain the same account-owned regular file throughout the read, and must predate that exact process. Its API socket must report that dockerd process and desktop UID as its peer. Every later target Docker command reconnects through `/proc/$pid/root`, and privileged volume work enters the same process's user and mount namespaces after rechecking its executable, start identity, and socket peer. The packaged executables, exact RootlessKit and dockerd arguments, fixed `/usr/bin` service `PATH`, and fixed `~/.config` configuration root must match Omarchy's known policies because Docker inspection does not expose defaults such as daemon-managed init, DNS, stop timeouts, or RootlessKit sandbox changes. The legacy rootful bridge resolver is deliberately translated to RootlessKit's namespace resolver; other daemon DNS policies require an explicit migration. An existing Windows container is reconciled from the hardened Compose definition while a root-only, synchronized lifecycle record preserves whether it was running or stopped across interruption; ambiguous Compose interpolation and unsupported legacy YAML escapes require the user to set the values explicitly. The new runtime must use web protection and the current account's protected mount anchors. Only after those checks does the migration durably claim the machine-wide source inventory for that account. A container named `omarchy-windows` is exempt only when its image, Compose identity, devices, capabilities, ports, environment, and UID-bound mounts match Omarchy's managed VM. A blocker in any source prevents the batch from stopping its first container or assigning the migration owner. Compose, credentials, the runtime directory hierarchy, legacy-definition removal, owner selection, and machine completion are synchronized to disk before migration continues.

The automatic path accepts running or never-started containers with stock bridge networking, localhost-only unprivileged published ports, private local named volumes, supported resource limits, root users with Docker's default capability ceiling or stricter settings, numeric non-root image users that already drop every capability, and the stock runtime and namespace boundaries. It rejects already-exited containers whose historical exit state cannot be recreated without rerunning them, privileged containers, added capabilities, devices, host or shared mounts, named image users whose effective UID is ambiguous, numeric non-root image users whose capability ceiling cannot be reproduced exactly, custom networks, namespace sharing, custom runtimes, altered confinement, custom logging, reserved migration labels, and unknown nondefault host settings.

For each accepted container, the migrator records the live init process's effective `nofile` limit when the source is running and uses a bounded source probe only for a never-started workload. It proves rootless Docker can reproduce every distinct limit before stopping the first source. The migrator then stops each source cleanly and durably seals its source-volume fingerprints before rootful Docker is restarted to revoke existing clients. Every seal is checked again before the first destination transfer. Source volume roots are resolved through dockerd's mount namespace; a root-owned helper requires a real directory, rejects nested filesystems, pins the directory descriptor, and uses descriptor-relative traversal for fingerprints, cleanup, and archive validation so a raced child symlink cannot escape the volume. The migrator journals an unpredictable image tag before committing the writable layer, records each source and destination image identity around Docker's native save/load transfer, and requires the loaded identity to equal the committed source before it cleans only copies that still prove ownership. A completed destination retains that tag as its exact image reference, while the source transfer copy is removed. Before the first owned destination volume can exist, the migrator durably journals and creates a unique event marker. The same event window remains active across recoverable failures and retained-volume retries, and its complete history is checked before retry cleanup, before retained data is cleared, and again before the completion receipt. A missing marker with retained volumes, a transient mount by another container, or incomplete daemon history stops automatic migration. The migrator creates an unpredictable inert guard that pins every owned volume while contents and metadata are copied inside the RootlessKit user and mount namespace. The application container does not exist during that long copy. Copied volume filesystems are synchronized before completion metadata is published. After transfer, a stopped `runc` application container joins the guard on the verified volumes; the guard is removed only after Docker proves both references, and the application container must still be never-started before finalization. The event marker is removed only after the completion receipt is durable. Temporary read-only, networkless, capability-free containers built only from root-owned host runtime files measure daemon defaults and target compatibility. Each probe is journaled before its image exists, uses an unpredictable reserved label and image tag, exits and auto-removes after a short bound, and is verified and cleared before the next source inventory if the prior process was interrupted. Container and image cleanup are attempted independently. The destination disables daemon-managed init explicitly and carries each workload's recorded limit so rootless Docker cannot silently widen or narrow it. The migrator verifies environment, application config, runtime, limits, capabilities, mounts, ports, restart policy, logging, volume fingerprints, and lifecycle before writing a receipt bound to full source and destination snapshots. If one transfer fails, every later source that the batch already quiesced is restored in reverse order.

Immediately before publishing that completion receipt, the migrator re-inspects the exact destination returned by runtime verification and rejects any identity or snapshot change.

Before the destination is first started, an error removes only the exact journal-owned destination container and restores the source. The first journal directory entry, each journal update, and each rename are synchronized before they can authorize mutation. Journal-owned volumes remain available for ownership verification; a retry attaches each verified volume to the stopped destination before emptying and copying the current stopped source again, so a concurrent name replacement, partial transfer, or later source deletion cannot damage unrelated data or leave stale entries. Resume requires Docker to prove that the destination has never started and to replay the persisted event window before starting it. Once a destination start has been attempted, automatic retry and source restoration stop for manual recovery because either side may contain new writes. Publishing the durable completion receipt is an irreversible phase: any later image-tag or journal cleanup failure retains the valid destination and is completed on retry. Successful sources remain stopped with their restart policy disabled; they are retained in the rootful engine as recovery copies.
