# Face authentication on the Dell XPS IR camera

How Omarchy turns the Windows Hello IR camera of the Dell XPS 14 (DA14260), and probably of the XPS 16 (DA16260), into a second authentication method, and which layer each command owns. The user-facing pieces follow the fingerprint wizard, the lock screen gains a face context next to its fingerprint one, and the driver layer is the `hm1092-ir-camera` package ([omacom/omarchy-pkgs#1213](https://github.com/omacom/omarchy-pkgs/pull/1213)) until mainline catches up.

## Hardware

The IR camera is a Himax HM1092 monochrome sensor behind the Synaptics SVP7500 USB bridge (usbio), on the same I2C bus as the RGB OV08X40. Firmware enumerates it as ACPI `HIMX1092` (one id per module variant, only the fitted one with `_STA` present and enabled), and the in-tree INT3472 driver exposes the IR flood illuminator as `/sys/class/leds/HIMX1092_00::ir_flood_led`. The TI LM3643 flash driver the DSDT also lists (`TXNW3643`) reports absent on this family.

No kernel has a sensor driver yet; one is under review on linux-media. `ipu-bridge`, which gives the sensor its CSI-2 endpoint, lists it from mainline 7.3 (`IPU_SENSOR_CONFIG("HIMX1092", 2, 180000000, 180480000)`), and `linux-omarchy` carries that entry from 7.2.8-2; on older kernels the sensor never binds. The `intel-ipu7-camera` package (Intel's out-of-tree IPU7 drivers, hardware ISP, `v4l2-relayd` into `/dev/video50`) covers RGB only, but its `intel_cvs` module performs the ownership handshake with the bridge that the IR sensor also needs.

## Contracts

`omarchy hw dell xps ir camera` is a hidden, silent predicate like `omarchy-hw-fingerprint`: exit 0 on a Dell XPS whose fitted camera module is the HM1092 and whose flood LED is registered, 1 otherwise. It takes no arguments and needs no camera driver, so it answers before the setup has installed one. Fixture roots for tests: `OMARCHY_ACPI_DEVICES_PATH` and `OMARCHY_LEDS_PATH`; the DMI match goes through `omarchy-hw-match "XPS"`. The device Howdy reads is `/dev/video-hm1092-ir`, the stable path the driver package's udev rule gives the relay device whatever video number it got at boot.

`omarchy setup security face` runs in this order and stops at the first failure without touching later layers: hardware present, `/usr/bin/omarchy-face-key` present, the `hm1092-ir-camera` package installed (otherwise it installs it with `omarchy-pkg-add` and stops, asking for a reboot, since DKMS builds the sensor module once pacman is done and the module loads only after `camera-init` at boot, and for the setup to be run again), `/dev/video-hm1092-ir` present (otherwise it names the relay unit to check and the kernel the sensor needs), the question where the face should work (sudo, polkit and lock screen; sudo and polkit only; lock screen only), asked with `gum choose` before the long AUR builds, Howdy and pamtester from the AUR, Howdy's `compare.py` (a Howdy that ships only its native `pam_howdy.so` is refused: that module scans the moment PAM reaches it and cannot wait for the key), `device_path = /dev/video-hm1092-ir` set in Howdy's config, `sudo howdy add`, the key service's units copied into `/etc/systemd/system` with the socket enabled and the `face-key` Hyprland toggle on, verification with `sudo pamtester omarchy-face-verify $USER authenticate` through a service that asks for the face alone (`omarchy-face-match --wait`, no password prompt), exists only for that check and is removed right after, pass or fail (the user looks into the camera and presses the Copilot key), then the chosen stacks. A stack left out loses the face lines an earlier run put there, so running it again with another answer moves the face. Last, `/etc/omarchy/face.conf` is copied with the lock's default limits unless it exists, which also marks the setup done for the first-run invitation. Running it twice adds nothing twice and keeps an edited `face.conf`. Every file the setup owns whole ships in the checkout's `default/` and is copied root-owned into place with `install -Dm644`, the way `omarchy-apply-lock` installs its fingerprint units, so an Omarchy update ships changes to them: `default/systemd/system/omarchy-face-key.{socket,service}`, `default/pam.d/omarchy-lock-face`, `default/pam.d/omarchy-face-verify` and `default/omarchy/face.conf`. Only the sudo and polkit stacks are edited in place, since they belong to other packages, and a missing `/etc/pam.d/polkit-1` is created around the face block. Fixed paths are `/usr/lib/security`, `/etc/pam.d/*`, `/etc/omarchy/face.conf` and `/etc/howdy`; Howdy's layout is read from `pacman -Qlq howdy`, because the stable install is readable by root only.

Presence is not consent. A camera sees a face whether or not its owner meant to approve anything, while a fingerprint reader only answers to a deliberate touch, so a scan waits for a touch of its own: the Copilot key, read by root from the keyboard (see "The face key" below). sudo and polkit carry this block, inserted on top of their stacks, or directly below the last fingerprint (`pam_fprintd.so`) or FIDO2 (`pam_u2f.so`) line where there is one. Those wait on their own, and the face rides on the password prompt, so a typed password then reaches pam_unix without waiting for a finger or a security key first:

```
auth      [success=2 default=ignore] pam_exec.so quiet /usr/bin/omarchy-hw-laptop-closed
auth      optional pam_exec.so seteuid quiet stdout /usr/bin/omarchy-face-match --hint
auth      sufficient pam_exec.so seteuid quiet stdout expose_authtok /usr/bin/omarchy-face-match
```

The gate skips both face lines while the lid is closed. The hint registers this conversation's prompt with the key service and, once it is registered, prints "Press the Copilot key to use your face, or type your password." (`seteuid`: only root reaches the service, so a hint line from an older setup offers nothing). Then `expose_authtok` makes pam_exec show the usual password prompt (sudo renders it as its own) and hand the answer to the helper on stdin. Anything typed declines the face: the helper withdraws the prompt from the key service and exits without a scan, and `system-auth`'s `pam_unix.so try_first_pass` verifies the typed password from the PAM item pam_exec stored, so there is no second prompt. The Copilot key answers the prompt with an empty line, and the helper scans only if the key service confirms the key was pressed for this very prompt; an empty Enter is just an empty password, as without face. `sudo -n` and scripts get no prompt and therefore no scan. A scan that fails or finds no model ends that round: pam_unix is handed the empty answer, rejects it, and sudo says "Sorry, try again" and starts over with the hint, at the cost of one `pam_faillock` tally; typing the password at the next prompt works as usual. A typed password costs nothing. `stdout` feeds the helper's messages to the prompt, `quiet` leaves them to the helper. Omarchy's polkit dialog does not render PAM's info messages, so `shell/plugins/polkit` here is upstream's agent reading the face line from `/etc/pam.d/polkit-1` the way it reads the fingerprint line: while PAM waits for the password with the lid open, the padlock becomes a camera and the empty field says "Face or Password"; the Copilot key, which Hyprland hands to the dialog's `polkit faceKey` IPC call, clears the field, answers with nothing and reads as "Scanning face...", a failure as "No match". Only the asking form of the line is offered. The lock service's line carries no `expose_authtok`: the lock keeps it waiting for the key instead.

The setup treats the block as one unit: a stack that carries it exactly, below any fingerprint or FIDO2 line, is left alone; any other face lines, from a `pam_python` setup or from the version that scanned without asking, are stripped together with only the gate directly above them and the block is inserted fresh, so enrolled models and a fingerprint stack sharing the file both stay.

`omarchy face match` is the hidden helper behind those lines, like `omarchy-hw-laptop-closed` behind the gate. With `--hint`, and only as root, it registers the prompt with `omarchy face key wait --detach --tty` and prints the heads-up once that succeeded. Otherwise, for sudo and polkit, it reads the answer from stdin when stdin is not a terminal and either drops the prompt (`omarchy face key drop`) or takes the key's press (`omarchy face key take`); for the lock screen it waits for the key (`omarchy face key wait --lock`) and, once the key has started its scan, reports how the scan ended (`omarchy face key scanned --lock`). With `--wait`, and only as root with a `PAM_USER`, it waits for the key itself without reading an answer: the setup's face-only check. It replaces Howdy's own PAM module, so it keeps that module's refusals: before it registers a prompt or waits for the key, and once more before the scan, it refuses while Howdy's `[core] disabled` is true, while `ignore_ssh` is true (Howdy's default) and the conversation's process carries `SSH_CONNECTION`, `SSH_CLIENT` or `SSHD_OPTS` (pam_exec gives the helper an environment of its own), and while `omarchy-hw-laptop-closed` says the lid is shut, whatever Howdy's `ignore_closed_lid` says, as the clamshell gate does in sudo's and polkit's stacks; the lock screen has no gate, so the helper is its only one. Howdy's configuration is read from `/etc/howdy/config.ini` where that exists, else from beside `compare.py`, and a refusal is logged to auth. Only then does it print "Scanning face…", run Howdy's `compare.py` for `PAM_USER` with the system Python 3, print Howdy's own messages, log to auth, and exit with Howdy's status (0 match, 10 no model, 11 timeout, 12 abort, 13 too dark). An empty or unsafe `PAM_USER` fails before anything runs; an unreadable Howdy tree means the session user's own conversation, which elevates (see the lock screen). Reached through that elevation, where sudo's `env_reset` leaves no `PAM_USER`, it refuses unless `/etc/pam.d/omarchy-lock-face` exists: the grant serves the lock screen alone, and a user who chose sudo and polkit only gets no scan through it.

`omarchy remove security face` removes the face module and only the clamshell gate directly above it from sudo and polkit, deletes the lock service and then its grant in `/etc/sudoers.d` (unconditionally: that directory is root's alone, so its contents cannot be checked first), `/etc/omarchy/face.conf` and a verification service an interrupted setup left, each only where present, so it undoes any of the three setups, then stops and deletes the key service's units and turns the `face-key` toggle off, which gives the Copilot key back to the Omarchy menu, clears the invoking user's models with `howdy -U <user> -y clear` while the CLI is still installed, then drops `howdy pamtester` and the `hm1092-ir-camera` driver the setup installed, plus `pam-python` and with it Python 2 where an earlier setup installed them, the way the fingerprint removal drops `fprintd`. A failed clear stops the package drop. The user is resolved from `id`, never from `$USER`.

Without any face model, say after `howdy remove` took the last one, nothing locks anyone out: sudo and polkit still show the hint and the prompt, the key answers "No face model known" and starts the round over, and the password works at any prompt. The lock screen's attempts fail at once without lighting the LED, because Howdy checks for models before it opens the camera, while the password context is untouched. The way to stop offering face authentication is `omarchy remove security face`, which also clears the hint and the prompt.

## The face key

`omarchy face key` is the hidden service and its client, in Python like upstream's other long-lived helpers. A fingerprint reader turns a deliberate touch into the scan itself; a camera does not, so the touch is a key that no program can fake: root reads the Copilot key (evdev `KEY_F23`, which the key sends with Super and Shift) straight from each keyboard's `/dev/input/event*` node. Programs running as the user can neither read those nodes nor, without `/dev/uinput`, fake them, and keyboards made through uinput sit under `/devices/virtual`, which the service ignores. Hyprland's `face-key` toggle (`default/hypr/toggles/face-key.lua`, copied into `~/.local/state/omarchy/toggles/hypr` by `omarchy-hyprland-toggle`) rebinds the key from upstream's Omarchy menu to the polkit dialog's IPC call (`o.rebind` with `{ ipc = "polkit.faceKey" }`, like upstream's own bindings), so no window ever receives it and it can never end up in a password. A synthetic key through `hyprctl`, `wtype` or the shell's IPC reaches the dialog at most, which then answers with an empty password.

- `serve` runs as `omarchy-face-key.service` behind `omarchy-face-key.socket` (`/run/omarchy-face-key.sock`, mode 0600, root only, and the service accepts only peers of its own uid). It opens the keyboards only while a prompt waits, closes them when none does, and exits after 30 idle seconds, so outside a prompt nothing reads the keyboard. The unit allows `char-input` reads and no other device, no network, and a read-only system.
- `wait --pam-pid <pid> --user <name>` registers the PAM conversation's process (pid and start time, so a reused pid is a different prompt), logged with its command line, and waits. `--detach --tty` (the hint) returns once registered and keeps waiting in the background; on the key it answers sudo's terminal prompt with its kill character and a newline through `TIOCSTI`, which this kernel (`dev.tty.legacy_tiocsti=0`) allows to root only. pam_exec runs its command in a session of its own, where `/dev/tty` is nobody's, so the waiter opens the conversation's controlling terminal, found from its `/proc/<pid>/stat`; a conversation without one, like polkit's helper, gets no typed answer, and a terminal whose node cannot be opened fails the registration, so no hint promises a key that cannot answer. `--lock` (the lock screen) looks past sudo to the conversation that ran it, prints "Waiting for the Copilot key" once the service holds it, and gives up when `LOCK_WINDOW_MINUTES` from `/etc/omarchy/face.conf` have passed since the service saw the first lock check of this stretch (see below), on the boot clock, which counts suspend; a check registering past that is turned away. A waiter ends when its conversation's process exits or, for the lock, when the conversation closes its end of the pipe.
- `take --pam-pid <pid>` answers whether the key was pressed for that prompt within the last five seconds and consumes the press. The polkit dialog answers on Hyprland's copy of the key, which can bring its take before the service has read the press from the keyboard, so a take for a prompt that still waits holds its answer up to a second (`TAKE_WAIT_S`) for that press; `drop` forgets the prompt; `scanned --lock --pam-pid <pid> --status <n>` tells the service how the lock's scan ended, Howdy's status 0 being a match.
- One press serves exactly one waiting prompt. With several waiting, it serves none: all keep waiting, each sudo terminal and the lock screen say "Face refused: another program is waiting for the Copilot key too", and a critical notification to the user names every requester ("sudo pacman -Syu (from bash)", "a polkit dialog"). The standoff ends only when the user types a password or cancels, so a program waiting beside a real prompt never catches the press meant for it.
- While a lock check waits, nothing but the lock is on screen, so the press is the lock's alone: a prompt waiting meanwhile gets nothing, and sudo's terminal says "Face refused: the lock screen had the Copilot key moments ago". The lock keeps the key while the scan that press started runs, until the helper reports how it ended (`scanned --lock --status`, from an exit trap, so a lid shut after the key reports too), or for at most 15 seconds (`LOCK_SCAN_S`, the lock's own bound on a scan). A match gives the key back at once, since the face opened the lock. Anything else keeps it 5 seconds more (`LOCK_GRACE_S`): after a miss that covers the check's return 1.5 seconds later, and when the check goes away without a scan, as at a password unlock, it covers a press already on its way. Root cannot tell a password unlock from a program running as the user that ends the lock's check, by killing its PAM conversation, to catch that press with a prompt of its own; the grace is what stops it. Such a program could also wait with a lock check of its own through the lock's grant and take the press there, so a match in a stretch where a lock check went away without a scan gives the key back only after the grace too. The lock's window keeps counting from that stretch's first check.

## The driver package

`hm1092-ir-camera` is proposed for Omarchy's package repository in [omacom/omarchy-pkgs#1213](https://github.com/omacom/omarchy-pkgs/pull/1213), next to `intel-ipu7-camera`, which it depends on. Its README, installed as `/usr/share/doc/hm1092-ir-camera/README.md`, has the support matrix, the camera's one mode and the known limitations. It ships the DKMS sensor module, a relay that republishes the raw stream as GRAY8 on a v4l2loopback device and drives the flood LED, a udev rule and a WirePlumber rule that keeps the device out of PipeWire. The face relies on this much of it:

- `/dev/video-hm1092-ir` is the relay device, whatever video number it got at boot. The `video` prefix makes OpenCV hand the path to FFmpeg; OpenCV's own V4L2 reader fails on the loopback's buffers.
- Only root opens it, which suits Howdy, and no session process can watch the IR camera or feed authentication its own frames. One reader at a time: a second gets `EBUSY`.
- The LED is lit only while a reader streams, for at most 8 s per reader (`MAX_ILLUMINATION_MS` in `/etc/hm1092-ir-camera.conf`), after which the reader gets black frames until it closes the device; across readers it is lit for at most half of any minute. Howdy's default 4 s timeout fits in one burst, and a longer one only adds dark seconds.
- The relay unit is `hm1092-relay.service`, and `/usr/lib/hm1092-ir-camera/hm1092-relay --probe` prints what it resolved; the setup points there.
- The package builds no `ipu-bridge`: before linux-omarchy 7.2.8-2 or mainline 7.3 the sensor never binds, and the relay fails at boot.

## Lock screen

The lock is Omarchy's Quickshell plugin `omarchy.lock`, whose PAM conversations run in-process as the session user. `shell/plugins/lock` here is upstream's plugin with a third context added:

- `facePam` runs the `omarchy-lock-face` service. `faceConfigured` follows `/etc/pam.d/omarchy-lock-face` through a `FileView`, the way the password context follows its file: the setup writes it only after a verified enrollment, and only when the face is wanted on the lock screen, and the removal deletes it.
- While the lock offers the face, `facePam` waits for the Copilot key the way the fingerprint context waits for a finger: `syncFace()` arms it once the lock is secure, on wake, when the policy or the enrollment changes and every 30 seconds, and withdraws it once the face is no longer offered. The field offers the face only while root holds the check, from the key service's "Waiting for the Copilot key" line (`faceArmed`) until the check ends, so a check that ended, however it ended, leaves no offer behind; one root held that ends or fails without a scan waits again 1.5 seconds later, one that never registered, as with the lid shut, is left to the 30-second sync, so a failing helper cannot spin. Root scans when the key is pressed, in the dark too; the helper's "Scanning face…" line tells the lock a scan started, which wakes the display. Nothing scans on lock, wake or a timer alone, and Enter only ever submits a typed password. Howdy's own timeout ends a scan, the idle blank waits for a running one instead of cutting it short, and `faceAbortTimer` bounds a conversation that never completes; a refused key shows "Face refused" in the field, an error "Face unavailable", and a face Howdy does not know "Who are you?", which stands for ten seconds before the field says "Enter Password" once no scan is left (or returns to "Face or Password" while one is); typing clears each. Howdy reports a stranger only by its timeout and pam_exec turns every refusal into a system error, so the lock takes the helper's "Face detection timeout reached" line during a scan for a stranger, and an error without it for an unavailable face. After a miss the check waits again 1.5 seconds later if a scan is left.
- Each lock offers the face for `LOCK_ATTEMPTS` scans (default 1) within `LOCK_WINDOW_MINUTES` of locking (default 60), from root's `/etc/omarchy/face.conf`, read live; a missing file or a malformed value means the defaults. Every scan counts, a password unlock restores both for the next lock, and a scan's start reads the count and the clock afresh and stops the scan past either, since the display may have been dark, or the machine asleep, when the window closed; the key service's own bound on the boot clock covers the moments before the shell notices. A lock recovered after a shell restart offers no face: its age and spent scans died with the old shell. `FaceModel.js` holds the policy, tested in node.
- While the face is offered the empty field says "Face or Password" instead of "Enter Password", reads "Scanning face…" while a scan runs, and a camera hint sits inside the field's left edge, brighter during the scan, opposite the fingerprint hint; the password dots keep clear of both. Once the scans are spent the hint goes and the field says "Password (face failed)"; once the window has closed, "Password (face expired)".
- The user-level conversation cannot read Howdy's root-only tree, so `omarchy-face-match` re-executes its packaged copy through `/etc/sudoers.d/omarchy-face-match`: `%wheel ALL=(root) NOPASSWD: /usr/bin/omarchy-face-match ""`, the same shape as upstream's `omarchy-theme-browser` and `omarchy-dns` grants. Unlike those it does not ship under `etc/`, which the package installs on every machine: it lives in `default/sudoers.d/`, and the setup installs it only when the face is wanted on the lock screen, the way `omarchy-dev-link` installs its drop-in (a staged copy parsed with `visudo -cf`, then `install -Dm440 -o root -g root`), before the lock service, so the lock never offers a face its helper cannot elevate for. A setup run without the lock screen, and the removal, delete it after the lock service. The empty argument list forbids arguments, the privileged half takes the account from `SUDO_USER`, the unprivileged half first checks that `PAM_USER` is the session user, and the outcome is a verdict for PAM, never a session.

To try it from a checkout, `omarchy dev link <checkout>` points Omarchy at it, and `omarchy dev pkg test omarchy <checkout>` installs it as the `omarchy-dev` package from the PKGBUILDs in `~/Work/omarchy/omarchy-pkgs/pkgbuilds` (or `$OMARCHY_PKGBUILDS_DIR`), since PAM, the lock's grant and the key service name the helpers by their `/usr/bin` paths, which the link does not reach. The package is a copy, so it is built again after a change to a helper, and without arguments it builds `~/Work/omarchy/omarchy-installer` instead. Until [omacom/omarchy-pkgs#1213](https://github.com/omacom/omarchy-pkgs/pull/1213) lands, the setup's `omarchy-pkg-add` finds no driver: `makepkg -si` in that pull request's `pkgbuilds/hm1092-ir-camera` installs it, and a reboot loads the sensor before the setup runs. `omarchy shell lock status` then reports `face`, `faceState`, `faceAttempts`, `faceArmed` and `faceAuthenticating`, and the shell log carries `face-armed`, `face-attempt: n/limit`, `face-matched`, `face-no-match`, `face-refused`, `face-error`, `face-timeout`, `face-withdrawn` and `face-aborted` events.

## Known gaps

- The driver package has run on one XPS 14 so far (linux-omarchy 7.2.8-8 and 7.2.8-9, `intel-ipu7-camera` 1.0.6-3). If another machine's sensor fails to probe or stream, meros/hm1092-linux is the fallback sensor module (clean, mainline-style, both ACPI ids, but no hardware flip, so `ROTATE180=1`).
- The AUR package `intel-ipu7-ir-dkms` wraps the same fix pack but also replaces `intel_cvs` and ships the fix pack's Howdy patch; on Omarchy it would collide with `intel-ipu7-camera`, which is why this package takes only the sensor module.
- The key closes what the Enter left open: no program running as the user can start a scan, through sudo, pkexec or the lock's sudoers grant, without a finger on the keyboard. What remains is the fingerprint's own gap. A press when no prompt of the user's own is waiting goes to whichever prompt is, so the key is for answering a prompt on screen, never for trying out. The lock screen is the exception while it waits for the key and scans, and for 5 seconds after; once it no longer offers the face (its scans spent, its window closed) and those have passed, a press there goes to whichever prompt waits, as anywhere else, while the field asks for the password, not the key. After a password unlock sudo and polkit take the key 5 seconds later, after a face unlock at once; the password works throughout. A program that keeps a prompt waiting can also hold off the face for every real prompt, since each press is refused; the password still works.
- The Copilot key stops opening the Omarchy menu while the face is set up; Super + Space still does.
- sudo's prompt is answered by injecting into its terminal, so face works where sudo asks on the terminal; `sudo -S` and a graphical askpass fall back to the password.
- The IR module has no privacy LED, and the RGB camera's cannot stand in: the V4L2 core claims a sensor's privacy LED when the sensor registers (`v4l2_subdev_get_privacy_led()` calls `led_sysfs_disable()`), so writes to `/sys/class/leds/OVTI08F4_00::privacy_led/brightness` fail with `EBUSY` and only the RGB sensor's own streaming lights it. Only the prompt's or the lock screen's own text shows an IR scan.
- Upstream's fingerprint wizards take every `omarchy-hw-laptop-closed` line for their own gate: the removal deletes the face's gate too, and a setup beside the face leaves `pam_fprintd` ungated. [omacom/omarchy#15685](https://github.com/omacom/omarchy/pull/15685) makes them recognize their gate by its place directly above `pam_fprintd.so`, the way the face wizards do; the face's pull request waits for it.
- The setup stops for a reboot after installing the driver. Now that the kernel's `ipu-bridge` lists the sensor from boot, starting `hm1092-camera-init.service` and `hm1092-relay.service` may be enough instead; untried on the device.
- `pamtester` and `howdy` are AUR packages; `python-dlib` builds for a while. Howdy has not tagged a release since 2.6.1 (2020) although its beta with a native PAM module merged into master in 2025; `howdy-git` and the C++ `howdy-next` on the AUR are the candidates if the stable package falls behind.
- Howdy opens the relay device through OpenCV, which reaches it via FFmpeg's video4linux input. FFmpeg prints `ioctl(VIDIOC_QBUF): Bad file descriptor` when Howdy releases the capture, because it returns the last frame buffer after closing the device. Harmless; the frames were already read.

## Exit plan

The kernel's `ipu-bridge` already lists the sensor. Once a sensor driver lands in `linux-omarchy` as well, the package drops its DKMS module and its relay learns that driver's `Y10` format; Howdy, the PAM lines and the lock plugin stay, since the face depends only on the device contract above, not on which driver wins.
