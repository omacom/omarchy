# Boot splash and login screen

Omarchy draws the drive-unlock prompt at boot, and the login screen after it, with the same Quickshell window: the logo, the password field and a progress bar, in the theme's colors. The boot splash replaces Plymouth in a busybox initramfs; the login screen replaces SDDM and runs under greetd.

## The boot splash

`etc/initcpio/install/omarchy-splash` builds it into the initramfs from `default/splash/` (installed at `/usr/share/omarchy/default/splash/`): sway, seatd and Quickshell, the Qt and QML modules Quickshell loads, the XKB data and compose tables, touchpad and pointer kernel modules (I2C HID, Intel THC, PS/2 and I2C mice/touchpads, Synaptics RMI4, Intel LPSS/idma64 and laptop I2C/SMBus controllers, and Intel pinctrl GPIO IRQ drivers), the font a shown password is drawn in (Noto Sans Mono, from `noto-fonts`) and the pointer's arrow (Adwaita's, from `adwaita-cursors`, in each of its sizes), both at their own paths, and the scripts and `ui/*.qml` (all but `greeter.qml`) under `/usr/lib/omarchy-splash/`. There is no Mesa or NVIDIA userspace in the image: sway draws with wlroots' pixman renderer on the kernel's KMS drivers, and Qt Quick with its software backend. The baseline in `etc/mkinitcpio.conf.d/00-omarchy-hooks.conf` names the hook in place of `plymouth` on the busybox line once sway, seatd and Quickshell are installed, and Plymouth until then.

The hook's `run_hook` (with `splash` on the kernel command line, and not `plymouth.enable=0`, which turns off Plymouth's shutdown screens too) starts `session` in the background:

- It waits up to 8 seconds for a GPU's own KMS driver, as plymouthd does, then settles for the firmware framebuffer (simpledrm). Every native GPU with display connectors is drawn on, the firmware's boot display first; a render-only GPU (a Raspberry Pi's v3d) neither counts nor ends the wait.
- It keeps those GPUs out of runtime power management while the splash is up, since amdgpu powers a GPU with no display connected down, and it then misses a display plugged in.
- It writes sway's keyboard from what `layouts` made of `/etc/vconsole.conf` as the hook built the image (`/usr/lib/omarchy-splash/vconsole.conf`): its XKB settings with a plain US among the machine's layouts where they lack one (after them, or in front of a non-Latin one, below), and without layout shortcuts (`grp:` and `grp_led:` options), or libxkbcommon's defaults (US) when it names neither `XKBLAYOUT` nor a `KEYMAP` other than `us`. Passwords typed at Plymouth, non-ASCII ones included, type the same here, but for control characters, which the field drops (below).
- Plymouth read a `KEYMAP` without `XKBLAYOUT` from the tty, through the kernel keymap; the splash has no layout to type with for one. Setup and the ISO write the XKB layout kmscon types the password with at install: `kbd-model-map`'s, or for the keymaps that table lacks the lines `omarchy_keymap_xkb_settings` prints (`install/provisioning/setup-form.sh`). The splash's migration writes those on older installs before the first image, so the desktop, lock and login screens type that layout too from the next login. For any other `KEYMAP` without `XKBLAYOUT` the splash stays up but the password is asked on the console, where the keymap hook loaded the keymap.
- A first layout that types no Latin letters (`ru`, `ua`, `gr`, `rs`, ..., the list in `omarchy_hooks.conf`, #6229) starts in US instead: `layouts` moves the machine's US to the front, or puts a plain one there, and `vconsole.conf` itself stays out of the image (`omarchy_vconsole.conf`). For those, Serbian Latin included, kmscon starts the password step in US too, with the other layout a Shift+Shift away (`omarchy_keymap_xkb`), as the console's own keymaps start in Latin and the login screen and the desktop in US. A password typed as kmscon starts then types here too.
- It runs `seatd-launch sway`, whose one client is `ui-launch` running Quickshell on `ui/shell.qml`. When the firmware framebuffer goes away under it (the GPU's own driver bound late), it starts again on that GPU.

The encrypt hook, and the other hooks that talk to Plymouth, talk to `/usr/bin/plymouth`, which in this image is `default/splash/plymouth`:

- `--ping` answers whether the session is up, and `ask-for-password --command=...` writes a request that the splash shows. The splash runs the command with the password on its stdin through `answer`, which reports the exit status back, and a wrong password brings the field back in the error color.
- The attempt runs apart from Quickshell, so an unlock under way outlives the splash: `ask-for-password` waits for it, and a splash started again on another GPU shows its progress.
- `display-message --text=...`, as `omarchy-restore` sends while it restores a snapshot, shows the text under the field or the bar, the latest one only. Anything else is accepted and does nothing.
- The field shows dots, or the password itself when toggled with the eye inside its right edge or Tab (automatically hiding again after 15 seconds of inactivity, on submit or when the field hides), or while Alt+F8 is held. Keys follow Plymouth's line editing (`ui/Password.qml`), but control characters never go into the password, since a shown password can't show them. The pointer shows only once it moves with the field up.
- Where the machine has a layout other than plain US, a keyboard in the bottom-right corner names the layout being typed in, with its variant where two share a layout (Colemak and US), and a click, tap or Shift+Tab switches to the next, through sway's IPC (`xkb_switch_layout`). XKB layout shortcuts stay stripped so the corner always names the one typed in.
- Escape, at any point, or the session ending, moves the prompt to the console, where cryptsetup asks as it does without Plymouth. The power button powers the machine off while the splash is up in the initramfs (`power-button`); from the real root on, logind answers it.

As Plymouth does, the splash stays up while the real root boots. The late hook leaves it running and writes `omarchy-splash-stop.service` into `/run/systemd/system`, which the real root's systemd runs just before the login screen, a console login or an emergency shell. The stop unit omits normal boot dependencies so emergency mode does not discard it; a boot-only `emergency.service` drop-in resets the console's text and keyboard modes before the maintenance prompt, since the console stays in graphics mode after the stop (see [The handoff to the desktop](#the-handoff-to-the-desktop)). `stop` ends only the splash's own processes, those systemd didn't start: in the root cgroup in the initramfs, and in `init.scope` in the real root, where systemd moves them as it starts. A `seatd.service` of the system's own, in its unit's cgroup, is left alone. The hook also masks Plymouth's boot splash in the real root for that boot (`plymouth-start.service`), since the plymouth package stays installed. When the real root's crypttab lists a volume that asks for its passphrase at boot (one without a key file, and not `noauto`), whose prompt the splash would cover, the late hook takes the splash down instead.

The splash's output goes to `/run/omarchy-splash/session.log` and `ui.log`, which survive into the real root; `omarchy.splash.debug` on the kernel command line adds sway's debug log to the first.

### Updating the boot image

The image carries copies of the hook's scripts and QML, and of the programs and libraries it runs, and mkinitcpio's pacman hook rebuilds it only for kernels, firmware and `/usr/lib/initcpio`. The splash's own files, `/etc/initcpio/*/omarchy-splash` and `/usr/share/omarchy/default/splash/`, are among the inputs `omarchy-boot-sync-initcpio` hashes after an omarchy-settings update (`91-omarchy-initcpio-rebuild.hook`), so every boot image is rebuilt when one of them changed. The real root's `stop` and the image it stops therefore come from the same release. Omarchy's own pacman hook, `default/libalpm/hooks/90-omarchy-boot-splash.hook` (shipped by the omarchy package), runs `omarchy-update-boot-splash` after an upgrade of a program the image copies from another package, sway, seatd or Quickshell, or of the `/usr/lib/libwlroots-0.20.so*` sway draws with, so Omarchy's build of it (below) reaches the image whenever it lands. The real root's `stop` asks the image's Quickshell where its progress bar is with the real root's `quickshell ipc`, so the two stay the same version. The libraries these programs load trigger no rebuild, as Plymouth's didn't; Omarchy rebuilds Quickshell for each Qt update, which brings Qt's changes along. Where the HOOKS baseline names `omarchy-splash`, `omarchy-update-boot-splash` rebuilds every boot image through `omarchy-boot-rebuild` (`mkinitcpio -P` where Omarchy manages no boot loader), and nothing elsewhere. The migration that brings the splash in builds the first image, once the splash's runtime is installed.

### Multiple GPUs

Stock wlroots 0.20 draws with pixman only on the first GPU in `WLR_DRM_DEVICES`: the copy to another GPU's displays needs a renderer that imports DMA-BUFs. Omarchy's `wlroots0.20` package carries the copy patch: pixman renders into shared memory, and every GPU copies only what changed into dumb buffers of its own, so nothing is read back from device memory. The runtime depends on that package and the migration installs it before switching login or rebuilding boot images.

## The login screen

greetd runs `default/splash/greeter` as the `greeter` user: Hyprland with `default/splash/greeter.lua`, which runs Quickshell on `ui/greeter.qml`. It runs Hyprland itself, not `start-hyprland`, whose restart after a crash comes up in safe mode without the greeter; greetd starts a new greeter instead. `ui/greeter.qml` draws the splash's window for one user, the eye, Alt+F8 and Tab, and the layout keyboard and Shift+Tab included, sends the password to greetd, which checks it through PAM, and asks greetd to start `default/splash/login-session` (Omarchy's Hyprland under uwsm, with its output in the journal) before Hyprland exits.

The keyboard layouts come from `layouts`, as at the boot splash (`greeter` exports them), and the layout keyboard switches them with `hyprctl switchxkblayout`. Left Alt + Right Alt, which switched a non-Latin layout at SDDM's greeter, switches only on the desktop now. As at the boot splash, the pointer shows only once it moves with the field up.

`omarchy-system-login` writes all of `/etc/greetd/config.toml`: the user the login screen signs in, and autologin (greetd's `initial_session`, run once a boot). Both kinds of session run under the `omarchy-login` PAM service (`etc/pam.d/omarchy-login`; `omarchy-system-login` names it only once omarchy-settings has installed it, since greetd won't start if the service it names is missing), which sets `XDG_SESSION_TYPE=wayland` and `XDG_SESSION_DESKTOP=Hyprland` (`default/splash/login-session.env`) before `pam_systemd` registers the session, as SDDM did: greetd sets neither, and logind would record a `tty` session, whose idle state it takes from the VT. The installer turns autologin on for an encrypted install, where the LUKS prompt is the sign-in, and first-boot setup does so for one boot on an unencrypted one. `--from-sddm` carries SDDM's settings over on a machine that ran it; a pending first-boot autologin cleanup instead leaves greetd asking for login on the next boot.

Before greetd starts, `omarchy-system-wait-drm` (`etc/systemd/system/greetd.service.d/10-omarchy-wait-drm.conf`) waits for a GPU's own driver to replace simpledrm where it binds late, so neither kind of session starts Hyprland on a card that goes away under it.

After sleep, `omarchy-system-login-recover` (from drop-ins on systemd's sleep services) restarts the display manager when no session holds a local seat: a greeter or autologin that couldn't start while the sleep froze `user.slice` leaves greetd failed once systemd stops restarting it; SDDM stayed up without either (#19271).

## The handoff to the desktop

From the drive unlock to the desktop, the screen goes from the splash's last frame to the startup cover (`shell/startup-cover.qml`), which draws the splash's logo and bar where the splash did, without the console or a blank screen between them. Without autologin, the splash hands over to the login screen's window the same way; from there to the desktop the console still shows (see [Limits](#limits)).

### Progress

After Enter, the splash's bar eases out towards 70% over 4.4 seconds. Once the unlock succeeds it slows from its pace to rest at 65%, or where it already is after a slow unlock, over 1.1 seconds, so it is at rest when the splash stops about a second later. Before ending the splash, `stop` asks its Quickshell where the bar is, through Quickshell's IPC (`IpcHandler` `splash`, `progress()`, whose socket is in the splash's runtime directory under `/run/omarchy-splash`, so the real root can reach it), and writes the answer to `/run/omarchy-splash-progress`: the bar's value, or `none` where the splash showed no bar, as when nothing was unlocked. That costs about 0.1 seconds of the stop, a cold `quickshell` client, while the splash still draws; in the initramfs, whose busybox has no `timeout`, it can't ask. Quickshell's IPC has no version check, so a real root's `quickshell` from another build can fail to ask, which leaves no value.

The startup cover reads the file once. Its bar starts at rest at that value and runs on towards 95%, which only the reveal passes: when the shell is ready it fills the bar, fades out and quits. With `none` it shows no bar, and without the file it starts empty, as the splash's bar does after Enter. The login screen's PAM service (`etc/pam.d/greetd-greeter`) removes the file, since a login from there has no splash bar to continue; `/run` goes at reboot.

### The picture

- **The console stays in graphics mode.** In the real root, the splash's seatd keeps the initramfs as its root, whose `/dev` switch_root moved away, so as sway goes it most likely cannot reopen `/dev/tty1` to put the console back in text mode: the console stays in graphics mode, with its keyboard off. With `text_mode = false` in `[terminal]`, which `omarchy-system-login` writes, Omarchy's greetd leaves the console in that mode for the greeter and every session instead of switching it to text (a greetd without the key ignores it). It still clears the console, so whatever shows of it is blank, and the greeter's output goes to the journal (`omarchy-greeter`), as the session's does, rather than onto it. A console login (`getty`) and the emergency shell reset the console through `TTYReset=yes`; the greeter's and the desktop's Hyprland take it through logind.
- **The display stays lit.** The last close of a DRM device puts the kernel console's picture back (`drm_lastclose`), and the stop closes the splash's. `omarchy-splash-hold.service` (`default/splash/hold`), which the late hook pulls in from `graphical.target` alone, opens every card the splash's sway has open just before the stop, drops DRM master if its own open made it the master, and lets go once logind holds them all for a session, whose compositor keeps them open from there: the greeter's or the desktop's Hyprland, a second or two after the stop. It lets go 20 seconds after the stop at the latest, and at once when the display manager stops or isn't there (`BindsTo=display-manager.service`); a console login, rescue or emergency boot doesn't start it. It logs to the journal as `omarchy-splash-hold`.
- **Hyprland takes over the last frame without a modeset.** Omarchy's aquamarine, with `AQ_SPLASH_ADOPT=1` in the compositor's environment, adopts a display that is already lit in the mode Hyprland wants, picture and all. It also sends no empty (SDR) HDR metadata where the kernel holds none, as Hyprland commits on displays that support HDR, since i915 and amdgpu modeset for it. It adopts whatever is lit, so the variable is set, for the greeter's Hyprland and for the desktop session, only while the holder still holds, when the picture is the splash's: `/run/omarchy-splash-hold/adopt` exists from the stop until the first session takes a display, and `greeter` and uwsm's `env.d/10-omarchy` set the variable only while it does, so the splash's last frame goes to whichever comes first, the login screen or the desktop. A session started from the login screen doesn't get it: the console is back by then.
- **Hyprland keeps it until the next window is up.** On a display it adopted, Hyprland holds the adopted picture until a layer with the namespace `misc:startup_hold_layer` names is opaque, for 5 seconds at most: the startup cover's (`overlay:omarchy-background`, `default/hypr/looknfeel.lua`) in the desktop session, the greeter's window (`overlay:omarchy-splash`, `greeter.lua`) at the login screen. Displays it didn't adopt start as usual.
- **No cursor.** Hyprland shows its own cursor as soon as it starts, over the held picture, so the desktop session sets `cursor:hide_at_startup`: no cursor until the client under the pointer sets one or the pointer moves. The startup cover sets a blank one before its window shows (Quickshell's `WlrLayershell.cursorShape`), so the cursor first shows on the desktop. The greeter starts with `cursor:invisible` instead.
- **No zoom.** Hyprland's `monitorAdded` animation would zoom a display's first frames in over the held picture, so the desktop session turns it off, for displays plugged in later too; the greeter has no animations.

## Limits

- **The splash's root.** After switch_root the splash's processes keep the deleted initramfs as their root until the stop, and with it the image's sway, Qt and Quickshell in memory. The console-free handoff relies on that, so it stays as it is for now; giving the splash the real root needs the console's mode handled another way first.
- **From the login screen to the desktop.** When the greeter's Hyprland exits, logind switches the console back to text mode and the kernel's console takes the display, before greetd starts the session, so a blank console shows briefly between the two. The holder covers only the splash's handoff, to the desktop or to the login screen.
- **10-bit and wide-gamut monitor rules.** The splash's sway draws 8-bit SDR, so it leaves `max bpc` at 8 and the colorspace at its default. A monitor rule with `bitdepth = 10` or `cm = "wide"` changes them, which the kernel applies only with a modeset, so that display goes black once at the handoff.
- **A key file that can't be read.** systemd-cryptsetup asks for the passphrase on the console when a volume's key file can't be read (a USB stick that isn't plugged in), and the late hook can't foresee that, so the prompt is hidden under the splash and the boot waits there; Escape doesn't help in the real root, where the console keeps its keyboard off. Plymouth showed such prompts. A boot-only drop-in that orders `omarchy-splash-stop.service` before `systemd-ask-password-console.service` and pulls it in, with `TTYReset=yes` as `emergency.service` has, would fix it, once tested on hardware.
- **systemd-boot.** Untested with the splash, so refused rather than run: the `omarchy-splash` hook builds no image where `omarchy-boot-backend --managed` names systemd-boot, which also stops `omarchy-boot-switch` before anything that boots changes, and the splash's migration stops there before it changes anything. The ISO refuses to build an image with the splash beside `omarchy-boot-systemd`. Integrating the two is its own work.

## Colors

The boot splash and the login screen take only their colors from the theme. `omarchy-theme-set` runs `omarchy-theme-set-login`, which hands the theme's `background`, `foreground`, `accent` and `red` to `omarchy-theme-set-login-colors`. That runs as root under a passwordless sudoers rule for `wheel` and exactly four six-digit hex arguments (`etc/sudoers.d/omarchy-theme-login`), and writes the credential on the ESP for the boot splash (`loader/credentials/omarchy-splash.cred`, which systemd-stub hands the initramfs as `/.extra/global_credentials/omarchy-splash.cred`), then `/var/lib/omarchy/login/colors` for the login screen. In either, only `background`, `foreground`, `accent` and `error` lines with a `#rrggbb` value count, and the default theme's, Tokyo Night's, stand in for anything else. `omarchy-theme-set-login` skips the write when that file already holds the colors, so the writer adds a line to it when the ESP's copy did not take them, and the next theme change tries again. A user outside `wheel` changes neither. The root image sets its theme before there is an ESP to write to, so a new install's first boot draws the splash's default colors and `omarchy-provision-first-run` writes the theme's at the first login.

## Where Plymouth still runs

Plymouth draws the shutdown splash, the Omarchy icon on black whatever the theme (`default/plymouth/shutdown.png`), from its own shutdown units: they start it as the login screen stops, it takes the display once the desktop session lets go of it, and it follows the shutdown into the initramfs.

A systemd initramfs has no `run_hook`, so the hook cannot run in one: Apple Silicon's baseline keeps Plymouth, in that same look, for the unlock prompt, and no theme changes it. The ISO builds no pre-built UKI for an image with the hook, so a new install shows the splash from its first boot.

Plymouth's progress bar keeps its own pace: 90% in 4 seconds, filling to 100% as it quits. The splash's comes to rest at 65% for the startup cover to go on from ([Progress](#progress)), so the two differ by platform.
