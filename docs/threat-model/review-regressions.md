## Failed-start gate correction, September 10

`SandboxedPluginActivation` now projects pending placements into presentation-only config. It commits a successful request against the latest canonical config, never another pending request's placement. Failure/cancellation preserves prior saved intent, concurrent unrelated changes and reviewed approval. Never-presenting startup has an eight-second host deadline. Native cleanup clears only its matching epoch/unit reservation; it cannot retire a newer session or recover an interrupted denial. Failed systemd exec also retires its reservation without re-signing or revoking approval.

`plugin-activation-test.sh` executes the production lifecycle and placement methods for failure, success, concurrent requests/settings, retry/move, cancellation, stale completion, invalid/lost placement targets and conflicting config changes. The real private-display `startup` integration executes the production shell with a broken shared widget, a never-presenting custom worker, and repaired/re-reviewed retry. It checks actual saved config bytes, error state, retired service records, preserved approval and successful placement. Captures of failed and retried states were inspected. This replaces the earlier synthetic pending-handler probe as the failed-start gate evidence.

The complete native graphics/Qt suite passed uninterrupted with 125 library tests, one binary test and 67 integration test functions, selecting systemd, graphics, synthetic private audio, proxy and the synthetic media player. The complete adapter suite passed all nine tests, including the new startup integration. Counts include child fixture functions, not independent end-to-end attacks. The CLI suite and focused registry, activation, input and text-format checks also passed. Installed/physical and packaging evidence is not implied by these development-stage runs.

After the repeated-enable completion race correction, the production startup and bar integrations passed again. The full headless shell suite passed 245 of 246 test files; `config-test.sh` still fails because the selected external `omarchy-pkgs` checkout lacks the explicit install rule for `plocate-updatedb.service.d/10-omarchy.conf`. This is separate from the missing Ward package payload. The shell-suite result is not an all-green release gate.

## Follow-up review of 75856e3a

The reviewer independently reproduced the boundary corrections on a fresh VM, while identifying remaining lifecycle and reporting issues. The following corrections address that follow-up; default packaging remains deferred.

| Finding | Correction and evidence |
| --- | --- |
| Review/approval leaves the shell's isolation snapshot stale | Successful import and approval request canonical shell rescans. A refresh arriving during a scan is queued for a follow-up rather than discarded. CLI checks cover the refresh call; the offscreen real-QML registry fixture and `plugin-runtime-test.sh` cover queuing and identity classification. This is scan coordination, not a claim of atomic filesystem/IPC transactions. |
| Missing checkout hides a running worker | Shell inventory includes native instances no longer in the checkout registry. The CLI preserves their independently observed state and displays `running/error` alongside the checkout error. Production listing-method and CLI tests cover this; an `activeUnit` string is never treated as proof of running work. |
| Descendant hardlinks inside selected folders | Documented the residual: root/ancestor overlap checks do not recursively audit descendants. Such a link requires a same-account host actor, outside the worker model. Separate signing-key link-count checks do not imply general descendant detection. |
| Corrupt/unreadable approval or verification key prevents stop | Emergency discovery matches a generated systemd service's live main process to the exact store and plugin, then stops that service. The real `controller` integration freezes three authenticated controllers to prevent their ordinary authority polling from satisfying the test. Corrupt record, unreadable record, missing public key and unreadable public key cases each stop only the target, preserving the other plugin and another store's same-ID controller. Denial and damaged metadata remain, and revoke/remove still report repair required. Missing verification keys also cannot be mistaken for absent records during approval. |
| Stock-machine disable/remove without native payload | The bridge acknowledges revoke/remove only when the entire configured store is demonstrably absent. Existing state, dangling symlinks, invalid requests and unavailable authority-creating operations remain errors. Real CLI install → disable/remove and standalone no-runtime tests pass; missing-binary tests preserve existing approvals and checkouts. |
| Competing pending enable placements | A second enable while starting returns an explicit busy/error result and cannot replace the first accepted placement. Production-method tests verify one controller, one commit and first-placement ownership. An already-ready session may still accept a subsequent explicit move. |
| Zero outputs bypasses first presentation | First startup requires actual presented content; zero outputs alone cannot commit enable intent. A latched first frame allows an already-started service to survive later output loss. Production-expression checks cover both phases; real private-display activation/startup tests pass without the initial latch's binding-loop warning. |
| Isolation helper failure is an unexplained shell error | Catalog/list now reports unavailable isolation/provenance state, advises checking installed helpers and state permissions, and still refuses third-party loading. This dependency also applies to legacy trusted plugins and is documented explicitly. |

Verification for these changes: native library tests, all three real systemd controller tests, `./test/cli`, the focused plugin/installation/review/staging/activation suites and the real offscreen registry fixture passed. Four private graphical tests passed across activation/review, manager and failed-start targets; the final readiness-latch change was rerun through both activation tests and startup. A fresh installation can then make a new trust decision. Earlier uses of “monotonic” mean within the retained installation's lifetime, not a permanent tombstone after full removal.
