# Polkit authentication and session locking

Omarchy's desktop Polkit agent blocks authentication while the session is locked. The system PAM boundary prevents fingerprint and FIDO2 authentication through any Polkit agent while either the requesting user or authenticating administrator has a locked Hyprland session. Explicit password authentication through an independent terminal agent remains available, including over SSH. Fingerprint, FIDO2 and password authentication remain available when unlocked; the screen lock retains its own password and fingerprint PAM stacks. This policy concerns interactive Polkit authentication, not commands already authorized by root, authorization caches or policies that grant an action without authentication.

The shell's private authentication store cancels pending requests as soon as locking is requested and rejects new requests during lock discovery, locking and secure lock. The Polkit agent stays registered. `AuthenticationGate.qml` owns cancellation when the lock changes or a new flow arrives while blocked. Authentication services remain outside the public service map and shell object tree, including for lock clones.

The dedicated architecture-specific `omarchy-polkit` package owns `pam_omarchy_lock.so` and its root guardian. Package builds compile the module; setup and authentication never compile code or write runtime executables into `/usr`. Both stable and dev Omarchy packages depend on it, so switching supported channels retains the runtime. The companion `omarchy-pkgs` recipes must ship before releasing this source. Both selectable source versions must contain this policy integration before activating the migration; arbitrary historical source/package downgrades after activation are unsupported. `omarchy-apply-polkit` validates package ownership, then publishes the complete PAM policy in one atomic replacement under a shared lock. Fingerprint/FIDO setup passes its requested method into that same transaction, so a failed setup cannot expose a sufficient method before its guard. The existing vendor `system-auth` includes retain password fallback and faillock.

Each sufficient fingerprint/FIDO factor is preceded by a lock check. A denial skips that factor and continues to password fallback. The clamshell gate and fingerprint factor form one block, preserving the gate's relative jump. A successful sufficient factor retains its transaction guardian through the account check. Reaching password fallback explicitly stops that guardian, allowing a password exchange within a terminal without consuming a shared presence factor. Non-sufficient presence factors, continued PAM lines, presence factors hidden in includes, and unfamiliar PAM controls or token quoting require manual integration; setup refuses to rewrite them rather than weakening an administrator's policy.

The PAM module identifies the agent's UID from kernel credentials: the socket peer for socket-activated Polkit helpers, or the real UID for legacy setuid helpers. It additionally resolves `PAM_USER` to the administrator's UID and watches both identities, deduplicating equal UIDs. The selected identity cannot replace the initiating UID, and an identity change cannot reuse the original presence authentication. Root callers need no additional authorization. Other callers need a valid helper connection.

For each transaction, a root guardian discovers both users' real Hyprland processes and authenticates their Wayland socket peers against their PID, UID and installed root-owned executable. User-owned runtime files supply routing hints only. Neither environment variables, user flags nor logind's user-settable lock hint authorize a request. The guardian uses the host namespace view through `/proc/1/root` because Polkit helpers can hide home/runtime directories. It accepts an already-running, root-owned deleted Hyprland executable after a package upgrade.

The guardian subscribes to `hyprland-lock-notify-v1` without polling. It terminates only its pinned parent PAM helper, even if a legacy caller inherited ignored termination signals, when the compositor locks or disconnects, or when the agent closes its connection. Closing the agent connection also handles cancellation before a delayed helper starts. The descriptor is observed for hangup only; the guardian never reads passwords. Account management forces compositor roundtrips and checks the connection again before allowing authentication to finish. A lock transition invalidates the transaction even if the session subsequently unlocks. Parent-death handling and PAM cleanup stop the guardian after the transaction. Cleanup uses a pidfd for the guardian too, avoiding PID reuse even with inherited automatic child reaping.

Unknown lock state fails closed. A running Hyprland process without an authenticated endpoint or the lock notification protocol blocks authentication. Users without a Hyprland process can still authenticate outside the desktop. If a UID has several Hyprland sessions, a locked session blocks Polkit presence factors for that UID. A compromised compositor, arbitrary process injection into it, already-authorized root activity and upstream Polkit authorization policy are outside this boundary. PAM and compositor events are not an atomic commit protocol for every privileged action.

A successful authentication of the shell's own lock also resolves startup lock discovery, so an exhausted discovery retry budget cannot keep Polkit disabled after an authenticated unlock.

The lock's normal fingerprint invitation appears only after its own PAM conversation has reached the reader. Its layout keeps the same reserved space while waiting, and persistent failures retain the existing unavailable notice. Cancellation disconnects the old fprintd client so the lock can acquire the reader through fprintd's normal cleanup.

Focused tests cover the private store, real QML cancellation gate, lock service, indicator, Wayland event parser, queued lock events and rejection of fake socket peers. Live validation must also cover both default and independent agents, pending and new locked requests, password and fingerprint authentication, cancellation followed by fingerprint unlock, and fresh authorization afterward. The upstream libfprint virtual-device driver with the real fprintd daemon exercises disconnect cleanup; it does not establish physical-reader behavior. Fresh ISO installation, ARM execution and physical fingerprint/FIDO hardware require their own validation.
