# Polkit authentication and session locking

Polkit authentication is blocked while an Omarchy user's Hyprland session is securely locked. Fingerprint, FIDO2 and password authentication remain available when unlocked; the screen lock retains its own password and fingerprint PAM stacks. This policy concerns interactive Polkit authentication, not commands already authorized by root, authorization caches or policies that grant an action without authentication.

The shell's private authentication store cancels pending requests as soon as locking is requested and rejects new requests during lock discovery, locking and secure lock. The Polkit agent stays registered. `AuthenticationGate.qml` owns cancellation when the lock changes or a new flow arrives while blocked. Authentication services remain outside the public service map and shell object tree, including for lock clones.

The system PAM boundary also applies to other Polkit agents. `omarchy-apply-polkit` installs `pam_omarchy_lock.so` and its root-owned guardian, then atomically places requisite checks before authentication and account management in `polkit-1`. It preserves existing authentication methods, their relative order, system-auth includes and administrator configuration. Fingerprint and FIDO2 setup reapply this ordering after adding a sufficient method. Installation and the upgrade migration use the same helper. The native module is compiled for the target architecture during setup using the default base-devel toolchain; authentication never compiles code or installs packages.

The PAM module identifies the agent's UID from kernel credentials: the socket peer for socket-activated Polkit helpers, or the real UID for legacy setuid helpers. The user selected for authentication can be a different administrator and must not choose the desktop being checked. Root callers need no additional authorization. Other callers need a valid helper connection.

For each transaction, a root guardian discovers the user's real Hyprland processes and authenticates their Wayland socket peers against their PID, UID and installed root-owned executable. User-owned runtime files supply routing hints only. Neither environment variables, user flags nor logind's user-settable lock hint authorize a request. The guardian uses the host namespace view through `/proc/1/root` because Polkit helpers can hide home/runtime directories. It accepts an already-running, root-owned deleted Hyprland executable after a package upgrade.

The guardian subscribes to `hyprland-lock-notify-v1` without polling. It terminates only its pinned parent PAM helper when the compositor locks or disconnects, or when the agent closes its connection. Closing the agent connection also handles cancellation before a delayed helper starts. The descriptor is observed for hangup only; the guardian never reads passwords. Account management forces compositor roundtrips and checks the connection again before allowing authentication to finish. A lock transition invalidates the transaction even if the session subsequently unlocks. Parent-death handling and PAM cleanup stop the guardian after the transaction.

Unknown lock state fails closed. A running Hyprland process without an authenticated endpoint or the lock notification protocol blocks authentication. Users without a Hyprland process can still authenticate outside the desktop. If a UID has several Hyprland sessions, a locked session blocks interactive Polkit authentication for that UID. A compromised compositor, arbitrary process injection into it, already-authorized root activity and upstream Polkit authorization policy are outside this boundary. PAM and compositor events are not an atomic commit protocol for every privileged action.

The lock's normal fingerprint invitation appears only after its own PAM conversation has reached the reader. Its layout keeps the same reserved space while waiting, and persistent failures retain the existing unavailable notice. Cancellation disconnects the old fprintd client so the lock can acquire the reader through fprintd's normal cleanup.

Focused tests cover the private store, real QML cancellation gate, lock service, indicator, Wayland event parser, queued lock events and rejection of fake socket peers. Live validation must also cover both default and independent agents, pending and new locked requests, password and fingerprint authentication, cancellation followed by fingerprint unlock, and fresh authorization afterward. The upstream libfprint virtual-device driver with the real fprintd daemon exercises disconnect cleanup; it does not establish physical-reader behavior. Fresh ISO installation, ARM execution and physical fingerprint/FIDO hardware require their own validation.
