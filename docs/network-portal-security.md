# Captive portal TLS security

## Scope and behavior

This assessment covers certificate handling in `bin/omarchy-network-portal-signin`, not an Omarchy-wide security assessment or a claim of STIG compliance. The portal uses an ephemeral WebKitGTK context and the platform trust store. It does not install certificate authorities, grant certificate exceptions, change the TLS error policy, filter certificate error flags, or retry failed HTTPS requests as HTTP.

WebKit's default TLS policy is `FAIL`. With no application `load-failed-with-tls-errors` handler, a TLS failure reaches the existing `Portal.on_load_failed` handler and terminates that load. Returning `True` from **WebKit's load-failed signal** handles the error presentation; it does not accept a certificate. This differs from the lower-level GIO/Soup `accept-certificate` signal, where returning `True` would authorize an invalid certificate.

HTTP discovery remains an independent entry point. Each launch and explicit browser handoff reads the running NetworkManager daemon's `ConnectivityCheckUri` over D-Bus. A credential-free HTTP URI is used unless it is malformed or under the known HSTS-covered `archlinux.org` or `gnome.org` domains; otherwise discovery starts at `http://neverssl.com/`. The browser button never forwards the rejected HTTPS URL or a network-supplied command. Neither button nor keyboard reload grants trust. After a failed navigation, WebKit may reload the last committed page; the application does not rewrite the failing URI. A successful commit clears the previous error footer.

Invalid HTTPS portals are intentionally inaccessible in this view. Legitimate HTTP portals and HTTPS portals with valid certificates remain supported. HTTP discovery and HTTP sign-in are unauthenticated transport; removing the certificate override does not make them secure HTTPS. The external browser retains its own security policy.

## Defect and adjacent review

At PR head `3599f849f068e7a89d6d5c956411ee115b4155ea`, `Portal.on_tls_error` replaced `pending_certificate` on every failure, but created `trust_prompt` only when absent. Failures for host A then host B left A's label attached to a callback that consumed B's certificate tuple. A safe replay of the actual handlers reproduced that mismatch. The acceptance callback also retained the tuple after use. Even with correct host binding, that callback could waive identity, expiry, revocation, and other validation errors.

The patch deletes the prompt, pending tuple, TLS signal callback, and acceptance method. There is no deferred certificate authorization left to bind, cancel, replay, or expire. The ordinary load-failure handler reports the error; subsequent successful navigation resets its footer.

The script also attempted to enable `allow-running-of-insecure-content` and `allow-display-of-insecure-content`. Those properties are absent from the inspected WebKitGTK settings API and the tested installation; the existing `TypeError` handler silently discarded the calls. They are removed rather than replaced with mixed-content exceptions. Top-level HTTP discovery does not require weakening HTTPS mixed-content protections. Existing file-origin restrictions, the ephemeral context, argv-based browser launch, and scheme validation remain in place. These settings alone are not proof that every filesystem interaction or download is impossible.

## Discovery and sign-in integration

This combines the opt-in opening behavior proposed in [#13745](https://github.com/omacom/omarchy/pull/13745) with the discovery problem described in [#11961](https://github.com/omacom/omarchy/issues/11961) and [#11966](https://github.com/omacom/omarchy/pull/11966). `autoSignIn` defaults to false. `PortalState.js` shares one automatic-launch claim across network panels, including newly added screens. Disconnecting, changing the connection, or recovering full connectivity rearms it; a temporary limited/unknown result does not. A manual launch consumes the same claim.

The discovery URI comes from [NetworkManager's live D-Bus property](https://networkmanager.dev/docs/api/latest/gdbus-org.freedesktop.NetworkManager.html), not a cached or lowercased configuration-file parse. [Chromium's HSTS preload source](https://chromium.googlesource.com/chromium/src/+/main/net/http/transport_security_state_static.json) includes `archlinux.org` and its subdomains. GNOME's parent domain advertises HSTS with `includeSubDomains`. [NeverSSL](http://neverssl.com/) publishes an HTTP-only discovery service. In an isolated installed Chromium profile with loopback DNS mapping, the Arch probe produced no HTTP request while NeverSSL reached the synthetic HTTP sign-in page. No browser security warning was bypassed.

The known-domain exclusion is not a complete HSTS database. A custom configured endpoint may still be upgraded by a browser's preload list, remembered policy, or HTTPS-only preference. The administrator should configure an HTTP probe suitable for captive discovery. NeverSSL is a third-party dependency: when the network does not intercept discovery, that service receives the request and client address. Neither it nor NetworkManager's URI is a trust anchor. Discovery does not alter the NetworkManager configuration or turn a rejected HTTPS request into HTTP.

User-initiated popup navigation uses a related WebKit view in the same ephemeral context. WebKit handles the original navigation, preserving form POST bodies, cookies, and the browser's opener/noopener rules. Child views inherit the same validation behavior. Closing a child returns to the previous view; stale child callbacks cannot reopen it. There is no URL extraction into a new GET request.

The originating QML panel owns the sign-in process and stops it when that panel closes or is destroyed. It supplies its screen, card bounds, bar edge, and network interface. Auto-close checks that interface's connectivity rather than accepting an unrelated working connection. The explicit browser launch starts a separate session so closing the panel does not kill a newly started browser. Missing GUI dependencies fall back to the browser before opening the dropdown; they do not trigger an installation. This fallback is separate from TLS errors.

Placement tests cover top, bottom, left, and right bars, constrained screens, and the supplied monitor geometry. Full nested Hyprland visual verification remains unverified: the installed Cage/Hyprland pair could not negotiate the required `xdg_wm_base` protocol version. The native GTK screenshots and QML fixture do not establish multi-monitor or fractional-scale placement correctness.

## Backend evidence and limits

**PROVEN source behavior:** WebKitGTK initializes its website data manager with `WEBKIT_TLS_ERRORS_POLICY_FAIL`; WebKit's Soup networking rejects reported TLS errors unless an explicit exception or ignore policy exists. libsoup supplies the remote identity to GIO. The GnuTLS backend loads system trust and calls `gnutls_certificate_verify_peers3` with the expected DNS name or IP address during a session. That path validates the chain and peer identity and processes stapled OCSP responses; standalone certificate verification is not an equivalent substitute for handshake validation.

- [WebKitGTK 2.52.6 website-data-manager source](https://github.com/WebKit/WebKit/blob/webkitgtk-2.52.6/Source/WebKit/UIProcess/API/glib/WebKitWebsiteDataManager.cpp), `webkitWebsiteDataManagerConstructed`.
- [WebKitGTK 2.52.6 Soup network source](https://github.com/WebKit/WebKit/blob/webkitgtk-2.52.6/Source/WebCore/platform/network/soup/SoupNetworkSession.cpp), `SoupNetworkSession::checkTLSErrors`.
- [libsoup 3.6.6 connection source](https://github.com/GNOME/libsoup/blob/3.6.6/libsoup/soup-connection.c), `new_tls_connection` and the `server-identity` property.
- [glib-networking 2.80.1 TLS connection source](https://github.com/GNOME/glib-networking/blob/2.80.1/tls/gnutls/gtlsconnection-gnutls.c), `g_tls_connection_gnutls_verify_chain`; [trust-store source](https://github.com/GNOME/glib-networking/blob/2.80.1/tls/gnutls/gtlsdatabase-gnutls.c), `g_tls_database_gnutls_populate_trust_list`.
- [GnuTLS 3.8.13 API documentation](https://www.gnutls.org/manual/html_node/Core-TLS-API.html), `gnutls_certificate_verify_peers3`.
- [GLib certificate-error contract](https://docs.gtk.org/gio/flags.TlsCertificateFlags.html): a reported flag set can omit other certificate problems. No single flag, including `UNKNOWN_CA`, justifies an exception or proves the remaining checks passed.
- [WebKit TLS-failure signal contract](https://webkitgtk.org/reference/webkit2gtk/stable/signal.WebView.load-failed-with-tls-errors.html): the load finishes regardless of the handler return value; an unhandled signal produces `load-failed`.

**PROVEN native fixture behavior:** on Omarchy with WebKitGTK `2.52.6-1`, glib-networking `1:2.80.1-1`, libsoup `3.6.6-2`, GnuTLS `3.8.13-2`, and `GTlsBackendGnutls`, both GIO handshakes and the real WebKit view accepted the valid synthetic chain and rejected wrong identity, unknown issuer, expiry, combined errors, a revoked OCSP staple, and a missing Must-Staple response. An ordinary valid certificate without a staple was accepted. The test trust anchor existed only in a disposable namespace; the host trust-bundle hash was unchanged afterward. These results do not establish network CRL/OCSP fetching, persistent revocation caching, or fail-closed behavior for unavailable status on ordinary certificates.

**Deployment requirements / UNVERIFIED:** keep the TLS libraries, platform roots, and clock maintained; identify the actual backend and package versions on each target; establish status freshness, offline revocation policy, and approved roots if the deployment requires them. Do not infer those controls from a `REVOKED` flag definition or from this patch. The newer Arch package versions inspected during research were not the installed versions used for native verification.

## Regression evidence

Run `bash test/shell.d/network-portal-test.sh`. It invokes `test/shell.d/fixtures/network-portal-tls.py`, which imports the entire real portal script with inert GTK/WebKit dependencies and subprocess calls. It tests application actions at the documented signal boundary, including every current error-bit combination, an unknown future flag, and an incomplete diagnostic event. It does not implement or certify a TLS verifier. Static checks also reject dormant certificate-exception and TLS-policy code.

The suite fails with the original override restored. Mutation runs also detect certificate-exception calls, a selective `UNKNOWN_CA` exception, TLS-ignore policy, automatic HTTP fallback, mixed-content allowances, and silent error handling. A separate red/green test covers the stale footer after successful navigation.

Native verification used synthetic loopback servers, a private root/intermediate chain, a stapled revocation fixture, and the installed GIO/WebKit libraries inside a read-only Bubblewrap namespace with a private Cage compositor. The real `Portal.build_view`, header, load handlers, and reload handler were used; layer-shell placement was not exercised by that fixture. Native valid HTTPS and HTTP form submission, popup POST and JavaScript sign-in, popup TLS rejection, HTTP discovery, redirects, successive failing hosts, reload, cancellation, and teardown were checked. Full Hyprland layer-shell placement, physical keyboard focus, real captive portals, and deployment-wide revocation behavior remain **UNVERIFIED**. Final repository-suite outcomes belong in the accompanying review run record and must not be inferred from this focused security assessment.
