# Agent usage records

`omarchy-agent-usage-update` writes each collector's JSON record atomically to the usage directory. `shell/plugins/agents/Agent.qml` watches those files. The top-level record keeps `schemaVersion: 1` and the established numeric fields for existing consumers.

## Usage-only collection and remote records

`omarchy-agent-usage-codex --stats-only` and `omarchy-agent-usage-claude --stats-only` scan usage without reading login credentials or requesting account limits. `--force` also bypasses the local scan cache; `--limits-only` retains its existing cache-reuse behavior. Neither native collection nor machine management requires OpenCode or the `sqlite3` executable. Python's standard-library `sqlite3` module remains part of the collectors' normal local runtime.

`OMARCHY_AGENT_SOURCE_ROOT` overrides the home used for Pi/OMP session discovery and enables the private sanitized OpenCode-import adapter; without that explicit variable, local OpenCode behavior continues to read its existing SQLite source. The remote backend sets the variable to its local sanitized-source directory and also sets `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `KIMI_SHARE_DIR`, `XDG_DATA_HOME` and `XDG_CACHE_HOME` so the collectors read only that machine's local metadata copy. Native and Claude aggregate files are supplied through read-only SFTP; no Agents collector or database helper is installed and no Agents-owned output/cache file is written remotely. Claude aggregate fallback retains only dated model totals, aggregate counters, and history timestamp/session IDs. Missing token categories are explicit and cannot be priced as zero.

OpenCode is not a prerequisite. An absent standard database path is silent and does not require an OpenCode binary or `sqlite3`. A present database enables a separate capability-gated SSH query only when the connected account can run an already present compatible `sqlite3`. The target's SQLite JSON functions execute the fixed scalar projection; conversation metadata is otherwise sanitized and interpreted locally. The query uses `-readonly`, `PRAGMA query_only=ON`, `PRAGMA temp_store=MEMORY`, `-init /dev/null` so personal SQLite startup commands are not loaded, safe mode when supported, required JSON functions, and the supported `message(session_id, data)` schema. It returns at most 10,001 rows so the local 10,000-row bound can be detected, with an 8 MiB stdout limit and a process timeout equal to the lesser of 15 seconds and the current cooperative pass time remaining. Local validation retains only bounded scalar identity/model/tariff fields—including `inference_geo`—and safe integer token counts. No free message JSON, content, credentials, remote output/cache file, uploaded helper, `opencode db`, `immutable=1`, or SFTP database/WAL copy is used. Custom OpenCode database paths and other schema forms are currently unsupported.

A failed present OpenCode capability keeps its prior dated sanitized contribution, if any, and marks only the Codex/Claude source portions stale or unavailable; native and Kimi collection still run. Successful query output is validated, aggregated, priced, and persisted locally. The database and, when present, its sibling `opencode.db-wal` size/mtime/mode plus the sanitized local payload digest are cached, so an unchanged verified source does not rerun the SSH SQL query. A WAL appearance/disappearance or attribute change, database attribute change, or damaged local payload forces a new query; unreadable/unsafe WAL metadata is a provider-scoped gap. Neither DB nor WAL contents are copied. SFTP v3 supplies whole-second mtimes, so this is an attribute-based change detector rather than a transaction ID: a same-size rewrite within the same second, or any external rewrite preserving every observed DB/WAL attribute, remains unsupported. A WAL append that changes size is detected even when its mtime second and the main DB attributes do not move. SQLite read-only mode prevents logical database changes, but ordinary reader coordination is not zero-cost: WAL readers may use or create the normal shared-memory index and delay checkpoints/WAL reset, while rollback-mode readers can briefly delay a writer commit. The process/output/row bounds limit, but do not eliminate, those effects.

Global session failures are different from source errors: expiry of the SFTP deadline, a broken SSH/SFTP stream or an invalid connection-level protocol response aborts the pass. The backend reports `unavailable` before the first successful import and `stale` for an existing snapshot, preserving its `lastSuccess`, provider records and last assembled result cache. A transport failure at an optional-source probe is not evidence that OpenCode or another optional source exists or is unreadable. Per-file metadata already committed locally can be reused on a later pass, but no partial failed transport pass is published as a successful machine snapshot.

Remote inventory and file failures are isolated by source root/file. Unreadable or unsupported roots, symlinks and unreadable JSONL files produce coverage issues; readable independent files continue. A malformed complete JSONL record is skipped and counted as an incomplete source while later valid records in that file continue to import. The cumulative invalid-record count is included in each sanitized progress checkpoint, survives resumed and warm-cache passes, and clears after a clean replacement. A wholly invalid replacement never displaces the last verified sanitized contribution. No symlinked source or source parent below the verified canonical home is intentionally followed. An incomplete inventory cannot establish deletion: its previously sanitized files remain until successful inventory and reads can replace or remove them. The retry replaces each source file in place, so recovery does not add its cached contribution twice. A completed sanitized file receives the original remote mtime immediately before atomic promotion because the established Codex legacy window uses that file metadata; unfinished progress files do not. Remote source contents and collector stderr are not included in diagnostics.

Collector processes are isolated by provider. A failed process or invalid result retains that provider's last successful record while other providers advance. A later refresh retries failed collectors even if the sanitized inputs have not changed. An initial failure without a prior contribution carries unknown tokens and incomplete `dailyUsage`, not measured zero. Known usage from a partial collector result remains available with its existing coverage issues.

In remote provider records, `remoteSources` maps source roots to `status` (`current`, `stale`, `unavailable`) and, when known, `lastSuccess` in Unix seconds. For each root, `lastSuccess` is the time of the last completed inventory and file/cache validation pass, including an unchanged root or verified absence. It is not a file-change timestamp and does not imply that cached stable file contents were reread. A failed root retains its earlier successful timestamp even when other roots advance; some readable files within that root may be newer. `remoteCollector` describes the provider process result with the same fields, but its timestamp advances only when that collector actually runs successfully, not when its cached result is reused. The machine's `lastSuccess` records the most recent assembled snapshot, not proof that every source is fresh; consult its `issues` and provider coverage. Root failures mark the affected provider's `dailyUsage.complete` false. These coverage/freshness annotations are applied to the outgoing record, leaving the cached successful contribution available for recovery.

`omarchy agent machine list` reads the catalog and cached snapshot without creating or rewriting runtime state. A refresh that is not due does not replace the panel's `state.json` or advance its timestamp. Catalog mutation and refresh publication share a lock; refresh takes membership and previous records from one snapshot and filters late results against the current catalog.

### Incremental refresh and continuation

The backend validates source size, modification time and mode. Stable unchanged files reuse sanitized metadata without reading file payloads; an unchanged source set reuses collector results. A recently modified file receives conservative head/tail validation before becoming stable, without rewriting unchanged metadata or rescanning collectors. An append validates up to 4 KiB of head and 4 KiB of the committed tail, then reads from the last complete JSONL record. Partial final lines remain only in memory and are reread when the file grows; unchanged partial files are cached too. Shrinkage, changed same-size mtime or a mismatched fingerprint restarts that file from the beginning. Equal-size edits preserving mtime/mode and sampled fingerprints remain outside this attribute-based detection contract.

Each machine pass has a 64 MiB SFTP file-payload budget, including fingerprints, native/aggregate JSONL chunks and the monolithic Claude stats payload. It has a cooperative 45-second inventory/transfer work limit checked between operations. The existing hard 120-second SFTP session deadline still classifies a connection failure. Transfers read at most 1 MiB per chunk; complete records and an unfinished line are limited to 16 MiB. Directory pages are consumed incrementally, with the existing 100,000-entry limit per source root. At most two machines import concurrently. Optional OpenCode SQL stdout is not an SFTP file payload and therefore is not charged to the 64 MiB counter; it has its own 8 MiB/10,000-row bounds and runs for at most the lesser of 15 seconds and the cooperative time remaining. Collector processes still have separate 60-second timeouts per provider and are not included in the cooperative transfer limit. These distinct bounds do not imply constant-memory processing of arbitrary history.

A separate local `progress/` cache checkpoints complete sanitized records, byte positions, size/mtime/mode and SHA256 fingerprints after each chunk. It never persists raw partial lines, prompts or transcript bodies. A resumed pass validates its prefix/tail and truncates any uncheckpointed local metadata before appending. Replacement invalidates tentative progress. Completed source files can advance locally between passes, but an unfinished pass never replaces the machine's last assembled provider snapshot or its `lastSuccess`. A process/transport interruption can lose the current chunk and unfinished record, not all previously checkpointed file work; checkpoints are not a power-loss durability guarantee.

Intentional budget exhaustion is `importing`, with `nextAttemptAt` set 60 seconds after a pass that advanced complete records, or 300 seconds without progress. Actual transport failures remain `stale`/`unavailable` and return to the ordinary hourly cadence; they do not inherit continuation scheduling or create optional-source issues. CLI `refresh` honors these due times; `refresh --force` runs immediately. The panel checks due times on startup and once per minute, starting no process for an empty/not-due catalog. Ordinary successful or failed attempts are due after 3600 seconds. Thus automatic continuation normally starts after 60–120 seconds (300–360 without progress), subject to an already running refresh. Manual requests made during a panel refresh are queued and coalesced; selecting All/local/a computer only changes presentation and performs no fetch. CLI-only installations require invocation of `refresh` by their caller; the command does not install a background service.

Daily buckets use the displaying process's local timezone. Collector cache keys include the local date, timezone names, UTC/DST offsets and `TZ` specification: a midnight or timezone change rescans local sanitized metadata without redownloading unchanged source contents. Offset-free timestamps remain unallocated/incomplete. The existing rolling daily coverage contract still applies when an offline snapshot ages; this does not introduce an all-time history policy.

A pass that cannot finish even the inventory or one complete permitted record within the work/transport budget cannot checkpoint that unit. It backs off instead of retrying in a tight loop; directory traversal itself is restarted on the next pass. Slow-link or unusually large-inventory behavior still needs remote validation. The synthetic harness `python3 test/shell.d/agent-remote-benchmark.py "$PWD"` measures first/unchanged/append passes through the production SFTP and collector boundaries. Its file-payload byte counts exclude SSH/SFTP framing and directory metadata; CPU and peak RSS describe local fixture processes, not an actual remote computer.

The remote transport tests use a local OpenSSH `sftp-server -R` process, never a real SSH connection. The runner searches common `lib`/`libexec` installation paths and accepts `OMARCHY_TEST_SFTP_SERVER` as an explicit executable path. If unavailable, it reports skipped Python transport cases while still running the JavaScript view tests. Permission-denial cases require an unprivileged Unix account. Linux local-machine rejection is skipped when `/etc/machine-id` is absent; the simulated Linux/macOS identity contracts do not constitute hardware validation.

## Native Codex daily data

The Codex collector additionally emits `dailyUsage`, an independently versioned consumption contract. Prices and subscription limits do not belong to this object. A consumer must not derive money from the legacy `recentDays.messageCount` field: its units depend on the provider/source.

| Field | Meaning |
| --- | --- |
| `schemaVersion` | `1`; consumers must reject unsupported versions |
| `unit` | `tokens` |
| `fromDate`, `throughDate` | Inclusive local calendar dates covered by the scan, currently the last 30 dates including today |
| `complete` | Whether every collected contribution has a verified date, token split and accounting identity; false is never evidence of zero use |
| `issues` | Scan-wide coverage problems that cannot be confined to a dated bucket |
| `unallocatedTokens` | Known measured tokens whose day/model cannot safely be assigned; not added to an invented day |
| `days` | Ascending local dates with `buckets`; an empty bucket list is meaningful only together with coverage and the recorded date range |

Each bucket contains `rawModel`, `source`, `sourceId`, `tariff`, `tokens`, `totalTokens` and `issues`. `sourceId` hashes the native session identity, or the existing legacy source identity, without exposing transcript paths. It is not a cross-device deduplication contract. Model identifiers are preserved rather than normalized into a pricing family. Missing, empty or non-string native identifiers are `null` with `missing-model`; only the legacy display name falls back to `codex`. `tariff` retains observed `service_tier`, `speed`, `fast_mode`, `cache_duration` and `inference_geo` attributes; their presence does not establish an applicable price. Missing attributes require a disclosed standard-tariff estimate when pricing becomes possible.

`tokens` has four disjoint fields: `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`. A nonnegative JSON integer is measured; `null` means unverified, not zero. Native input already includes cache reads and writes; the collector subtracts those categories once. Output already contains reasoning. Missing cache categories also make the remaining uncached input unknown. `totalTokens` can still be known from the source's input-plus-output quantities when the split is incomplete. Invalid JSON numbers, strings, booleans, negative quantities and inconsistent cache splits cannot substantiate complete cost coverage.

Native events retain their file-local model/tariff context and are reconciled per session in absolute timestamp order, independently of live/archive filenames and overlapping file traversal. Equal timestamps are ordered by measured cumulative quantity. Native cumulative counters act as session high-water marks. Repeated snapshots do not add usage, growing snapshots contribute only their increments, and a repeated archived copy sharing `session_meta.id` is deduplicated. Counter regressions are reported rather than treated as new requests. An initial cumulative history larger than the separately reported last request cannot be assigned wholesale to the latest model/day. Last-only records without a cumulative meter are explicitly marked as having unverified event identity. Missing current or previous cumulative cache fields can be filled from request fields only if the measured input and output increment equals the entire request; explicit invalid fields are not treated as omitted. A growing partial request cannot justify reusing its entire cache amount for an increment.

At unchanged measured input-plus-output totals, changes to quantities or cache classification add no consumption. Because a session-level correction cannot identify the affected historical day/request/model, `cumulative-correction` withdraws the category split of already collected session buckets (`null`) while preserving their measured `totalTokens`. Subsequent increments use the updated meter baseline. Existing numeric legacy category aggregates retain their prior split for compatibility; they are not pricing evidence, and their summed consumption does not grow on correction. Reasoning-only updates add neither tokens nor empty buckets/prompts. Independently known categories survive in numeric legacy fields even when the overall total is unknown; the daily contract retains `null` for unmeasured categories and total.

Native event dates come from valid timestamps converted to local calendar dates. Invalid timestamps never fall back to today or file mtime. Old file mtimes do not hide valid in-window events. Invalid undated usage makes scan-wide coverage incomplete. Consumers shifting a calendar window after midnight/resume must account for the scan's date range; they cannot assume that absent future dates have complete zero activity.

Legacy Codex sources keep their existing numeric records but contribute `source: legacy` buckets with unknown cost categories and `source-not-covered`. Their presence must not make a native-only subtotal appear complete. Likewise, older records or synchronized snapshots without `dailyUsage` have unavailable cost coverage; do not reuse a local cost total for a different synchronized token total. No original session history is rewritten. Native directory traversal reports errors explicitly; failed reads, malformed native records and errors from the existing Pi search make coverage incomplete. Rate-limit-only `token_count` notifications with `info: null` do not imply new usage. An absent source directory is distinct from an existing unreadable source. Pi parsing remains limited to the existing matching-provider search, and OpenCode remains the existing legacy adapter; this does not claim full coverage of sources deferred to later tickets.

The local scan cache retains envelope `schemaVersion: 1` and adds `collectorRevision: 2` to invalidate pre-reconciliation scans. Both public record and daily contract remain version 1. Cache reads validate versions, types, nonnegative safe integer quantities, complete-coverage claims, all 30 calendar dates, bucket structure and corresponding numeric legacy totals. Foreign record metadata inside cached stats is rejected. Unsupported, stale, future-dated or malformed caches cause a scan; scan/read/parse failures prevent cache writes so repaired sources are retried immediately. Legitimately partial token-category data may be cached with its coverage markers.

## Native Kimi CLI data

`omarchy-agent-usage-kimi` reads `<share>/sessions/<work-directory-key>/<session-id>/wire.jsonl`. `<share>` is the nonempty `KIMI_SHARE_DIR` value, otherwise `~/.kimi`; an override is used directly without tilde expansion. The CLI normally uses the MD5 of the UTF-8 work-directory path as its key, prefixed with the KAOS name for nonlocal work directories. The collector never imports Kimi, creates source directories, reads configuration/authentication files, or requires a `kimi` executable. Only actual positive measured usage supplies the session/activity statistics used by existing provider discovery; enabling or installing Kimi alone does not create data.

The supported format is Wire `1.10`, with a first-line `{"type":"metadata","protocol_version":"1.10"}` header and subsequent `{"timestamp":<Unix seconds>,"message":{"type":"StatusUpdate","payload":{"token_usage":{...}}}}` records. `input_other` excludes `input_cache_read` and `input_cache_creation`; `output` is total output. Cache fields default to zero when absent according to the upstream schema, while explicitly invalid values remain null. `input_other` and `output` are required. Context gauges and null/absent usage updates add no consumption. An invalid total retains independently known numeric categories, with incomplete coverage. No timestamp falls back to file mtime or today.

Every invocation performs a replacement scan, including `--force` and `--limits-only`; there is no persistent scan cache or content deduplication. Separate equal records count separately, and rescanning or truncating a file replaces its old contribution. Buckets carry a hashed source-relative file identity and physical record position. This is not proof of logical request uniqueness: fork/replay equivalence is unverified, subagent events and unexpected session assets are unsupported coverage gaps, and older/headerless Wire files are not silently interpreted as this version. Conversation/tool payloads are not retained in records, caches or diagnostics.

The additive `dailyUsage` contract above supplies 30 local calendar dates; Kimi uses its existing seven-day, top-four-model and Today/7/30 presentation. Historical model identity is not established by the supported event, so `rawModel` is null, tokens are displayed under `(unknown model)`, and costs stay unavailable with the shared limitation note. No current model configuration, alias or bundled price fills this gap. Exact manual model rates can be resolved by the shared formatter only for an independently established model identity; the current collector does not claim one. Other providers and synchronized cost-scope rules retain their existing behavior.
