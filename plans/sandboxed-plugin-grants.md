# Ward plugin grants

Ward is Omarchy's Rust-first plugin security system. This is its implementation inventory, not a claim of exhaustive ecosystem coverage or completed permissions. It supplements the [sandbox contract](sandboxed-quickshell.md) and [original-plugin compatibility ledger](sandboxed-plugin-winners.md). The vocabulary groups reusable resources and host effects; it must not grow one hardcoded permission type per plugin, helper executable or QML method.

## Required product behavior

This is a greenfield POC. Change its schema, commands and fixtures together; do not add readers, aliases, migrations or fallback branches for earlier sandbox prototypes. The sole existing plugin path is the reviewed, explicitly trusted v1 unpermissioned runtime. It remains separate from sandbox admission.

Permission expressiveness is a design goal, not a fixed list of broad booleans. Model exact resource identities, permitted operations and enforceable constraints. The target includes HTTP origins, methods, exact paths/path subtrees and query restrictions; exact files and directory scopes; and independently selected system-setting namespaces/keys and read/write operations. Keep enforcement code small without forcing a plugin to request broader authority than its workload needs. Unsupported scopes must fail explicitly, not silently become broader access.

Plugins declare required and optional requests. The user selects actual grants for the reviewed immutable revision. Missing required access prevents activation with a useful explanation; it never becomes implicit consent. Declining optional access permits activation and must be observable by plugin code through an admission-derived, runtime-readable grant snapshot. Worker modifications to that snapshot must not change authority. Updates and reapproval do not silently broaden or retain old access. Revocation stops the worker tree when directly bound resources must be withdrawn; it cannot undo completed writes, retract information already read, or cancel every previously accepted host effect.

Named resources must scale to practical workloads, replacing the prototype's eight-directory ceiling. Limits must follow tested transport sizes, open-descriptor budgets, mount setup and resource consumption. A larger schema limit alone does not prove that review, approval, persistence and worker startup can handle the same workload. Explain the effective limits and test their boundary.

Scope belongs in the type when it changes authority: resource root, access mode, recursion, service identity, allowed operations or network destination. Keep a boolean only when the supported capability is genuinely atomic. Every accepted scope needs actual enforcement and matching tests. Unsupported modes remain explicit gaps, not silently broadened grants or inert fields reported as completed features.

## Resource inventory

The original four plugins establish immediate requirements. Existing first-party shell code supplies additional plausible families; those observations are not a survey of all third-party plugins.

| Player publication and video capture | Plugin-owned MPRIS publication; selected camera, window or screen | Still prospective and separately sensitive. Audio playback does not publish a player; drawing does not imply any capture authority. |

| Raw device and bus access | USB/HID/serial, unrestricted sockets, session/system bus or device classes | Broader authority than a restricted device panel; document and mediate explicit scopes where feasible. |
| Full-authority integrations | Arbitrary host execution, credential-vault access, PAM/polkit/session-lock replacement and privileged changes | Not ordinary plugin-helper grants. Identify their trust implications and compatibility gaps rather than concealing them behind a convenient flag. |

Helpers, JavaScript, native modules, timers, private IPC and computation inside the worker do not each require a separate grant. Their effects remain constrained by the resources actually available to that worker. GPU rendering already exposes the selected render device and its acknowledged driver attack surface; it does not imply general device access.

## Implementation sequence and verification

1. Implement required/optional request semantics and admission-derived runtime introspection. Verify decline, missing required access, reapproval and restart behavior through the actual command and worker paths.
2. Implement typed selected-directory access and practical resource counts. Exercise actual reads/writes, file replacement and watching, denied sibling paths, helper inheritance and revocation with disposable host directories. Distinguish exact-directory scope from recursive path-beneath access and read-write from write-only guarantees.
3. Finish the existing browser/webapp grant. Verify the original helper names, literal argument preservation, explicit review selection, denied feedback, cross-grant checks and unchanged GitHub navigation in both modes. Success acknowledges host launch acceptance, not proof that a browser displayed a page.
4. Deliver the missing original-plugin resource families in coherent slices: authenticated GitHub operations, radio persistence/playback, pet persistence/sounds/system and geometry observations, and restricted AirPods status/control. Preserve each original source's behavior and record every adaptation in the winner ledger.
5. Extend prospective families only with concrete scope, enforcement and compatibility evidence. Keep the larger vocabulary in view without building an unused generic policy engine or claiming completion from schema-only placeholders.

Directory grants do not automatically authorize pathname sockets below them. Writable directories can alter real user data and may carry consequential authority if the user selects configuration or executable locations; review must explain that effect. Filesystem pinning prevents selection substitution but does not make directory contents immutable or undo authorized writes.

Network scope is a substantive enforcement problem. Ordinary HTTPS CONNECT or SOCKS forwarding does not prove HTTP path-prefix filtering inside encrypted traffic. Do not label a destination proxy as a URL-root policy without proving the claimed boundary. Evaluate compatibility with gh, curl, mpv, redirects, authentication and streaming before selecting mediation.

### Desktop geometry implementation

`desktopGeometry` is an optional/required atomic observation request, selected explicitly by `--allow-desktop-geometry` or the reviewer. It covers all supported output bounds, scale and reserved edges, workspace/output associations, and mapped/hidden/fullscreen window rectangles. Positions use global logical coordinates; IDs are opaque host-lifetime references, not raw compositor addresses. Titles, app IDs, process IDs, names, content and compositor commands are excluded. Rust validates the typed payload and filters both initial and live context before publishing it to a worker; a denied worker receives no geometry, including when other grants are selected. Unchanged filtered context is not republished merely because unselected geometry changed. There is no new worker socket or query service.

One trusted observer shares Quickshell's cached models across worker instances. Native Qt sequences are copied explicitly; initial polling waits for Quickshell's startup monitor query so a non-creating refresh cannot suppress its initial creating workspace query. Window refreshes are requested every 100 ms, monitor/workspace refreshes every second, with Quickshell's per-model in-flight guard. The projection is a latest-cache view, not an atomic compositor transaction. [Hyprland's monitor serialization](https://github.com/hyprwm/Hyprland/blob/v0.54.0/src/debug/HyprCtl.cpp#L186) supplies normal/special workspace membership and reserved edges in left/top/right/bottom order. The provider uses logical QScreen extents rather than raw monitor pixel dimensions.

The whole snapshot becomes unavailable for malformed, incomplete or oversized observations. Limits are 32 outputs, 256 workspaces, 256 windows and 48 KiB of geometry within the existing 64 KiB total context ceiling. The host preserves settings/theme/panel delivery by dropping geometry when the combined context cannot fit; it does not truncate individual lists. The admission snapshot distinguishes declined access from unavailable geometry. The [authoring reference](../docs/sandboxed-plugin-authoring.md#read-only-desktop-geometry) documents the current fields and coordinate conversion.

Maintained native and projection tests cover explicit/required selection, forbidden fields, finite coordinates, references, counts and the serialized byte ceiling. The real supervised shared-runtime test covers granted/denied geometry, live movement, settings and theme coexistence, restart and revocation. A separate real-Quickshell test uses private synthetic Hyprland sockets to verify logical-screen mapping, normal/special workspace association, stable QObject identity during movement and a new identity after closure/address reuse. The reviewer test exercises selection on/off, exact saved grants, activation, reopening with an unselected draft and revocation. These checks do not complete original-pet roaming, multi-output worker placement or final real-desktop acceptance.

Shared plugins may explicitly import `qs.Ward` for `Desktop`, a read-only compatibility adapter that checks the geometry permission itself. The generic real-worker test verifies declined/unavailable views, output and window projection, change signals, recovery, and failed writes to both the context and grants mounts. It does not shadow Quickshell's Hyprland module or expose compositor controls.

### Scoped HTTP implementation

The initial private transport experiment has now been followed by an implementation in `native/ward/src/http.rs` and the existing request broker. A manifest declares named `http` requests, each with a `scope` and optional `required` flag. CLI `--http <name>` and the reviewer select individual requested scopes; the store binds those exact scopes to the approved revision. HTTP access does not grant the broad `network` capability. An actual Bubblewrap child receives selected responses through the broker while remaining unable to connect directly to either the host fixture or a public address. Tests use disposable local APIs, not live accounts or credentials.

Scopes bind an exact origin and method, an exact path (with optional single-segment `*` matches) or a trailing-slash subtree, declared query keys with required/optional presence, and optional exact-field JSON bodies. Unknown and duplicate query keys are denied. JSON fields can bind exact values, bounded strings, nullable strings or nested exact-field objects. An exact GraphQL document plus declared variables prevents a worker from replacing or appending operations; `POST /graphql` alone is not read-only authority. The private proof exercised the original GitHub helper's authored-pull-request document, and maintained tests exercise document substitution, appended mutations and batching denial. See [GitHub's GraphQL call documentation](https://docs.github.com/en/graphql/guides/forming-calls-with-graphql).

The native HTTP client owns TLS and performs each request, with proxy inheritance, cookies and automatic redirects disabled; it does not forward a worker-owned tunnel. Domain resolutions are checked before those same addresses reach the connector. Common private, loopback, metadata and special address ranges are rejected for domain origins; literal IP origins explicitly select an address, including local APIs. Encoded or noncanonical paths are currently rejected. This conservative policy is implemented and tested, not a claim of complete URL compatibility or completed adversarial review.

The shared runtime installs `omarchy-ward-http`: one JSON request on stdin (`scope`, `method`, `url`, optional `body`), raw response bytes on stdout, and optional metadata in a worker-local file. Requests use one sealed descriptor and are limited to 64 KiB; responses use one sealed descriptor with at most 2 MiB of body and 4 KiB of framing/metadata. HTTP status and selected pagination/rate-limit headers are preserved; cookies are not. Direct bootstrap callers can prefix `--json` for one stdout record distinguishing Ward denial, invalid input, admission pressure, operational failure, timeout and unavailable replies. The record includes command stdout/stderr or HTTP headers/body, using UTF-8 strings or explicit Base64 objects for binary data. Completed HTTP responses retain `httpStatus`, including application errors such as 403; completed exec jobs retain `exitCode` or `signal`. JSON mode exits 0 for a completed outcome and 1 for Ward errors; raw mode retains ordinary command/HTTP exit behavior. No result file is created. Missing or incomplete results are unknown outcomes, never proof that an effect did not happen. See the [authoring contract](../docs/sandboxed-plugin-authoring.md#machine-readable-operation-results).

There are at most 32 declared scopes, twelve concurrent HTTP jobs per controller, and a ten-second broker job deadline. The shared connection admission ceiling is 32 per second across all broker operations; the HTTP operation budget does not override that lower shared ceiling. Unit tests cover schema, scope and sealed-record boundaries. Actual supervised-worker tests cover denied access, cross-operation rejection, binary and large-body delivery, scoped POST, redirect non-following, oversized-response rejection, twelve concurrent jobs plus busy rejection, timeout and in-flight revocation. Private Quickshell reviewer tests cover displaying and selecting the named HTTP scope, approval, activation, reopening and revocation. These are scoped-HTTP results, not proof of the original GitHub helper's complete API compatibility.

The structured-result integration cases invoke the actual bootstrap CLI inside supervised workers: missing grants and unmatched selections report `denied`, changed executable bytes report `failed`, a command exiting 1 reports `completed`/`exitCode: 1`, and a local API's 403 reports `completed`/`httpStatus: 403`. Binary command output and response bodies are preserved in JSON and raw modes. Default native tests, actual exec/HTTP/notification suites, and the CMake-staged private Quickshell shared-runtime check pass; the latter includes parsing a JSON denial through `StdioCollector` as well as accepted/rejected settings delivery. Concrete-plugin fixtures are not part of these Ward tests.

### Generic installed-CLI execution direction

Application-specific account providers do not belong in the plugin security core. The uncommitted GitHub credential-lookup implementation, account request/grant fields and account reviewer controls have been removed. Unknown account fields and the abandoned CLI flag are rejected, not ignored or migrated. The generic HTTP client currently supplies no host authentication.

The implemented path uses a declarative, positive-only command tree for explicitly granted host execution. The Rust broker matches an approved executable identity and a complete argument vector; CLI names and argument constraints are policy data, not provider-specific Rust branches. Named terminal leaves are independently selectable with `--exec name:leaf` or the reviewer. A terminal node permits only that complete invocation, not arbitrary trailing flags or every descendant command. Parent nodes group the declared leaves; they do not imply wildcard authority. There are no exclusions, deny overrides or rule-precedence semantics. Ordinary Quickshell Process and helper execution still inherit the worker sandbox. The packaged `omarchy-ward-exec` helper forwards a named request and literal argv through a dedicated broker socket; the worker receives binary-safe stdout, stderr and the installed CLI's exit status.

The matcher in `native/ward/src/exec_policy.rs` gives each tree node an optional named `end` and positive `next` steps; a step matches one argument before entering its `then` node. Constraints support exact strings, explicit alternatives, canonical unsigned integer ranges, byte-bounded text with a literal prefix, and bounded whole-argument regex patterns. Patterns cannot escape their outer anchors; pattern bytes, nesting, compiled size and input length are bounded. Limits are 32 arguments, 8 KiB per argument, 64 KiB total argument bytes, 512 tree nodes and 64 KiB serialized policy. Tests cover selected/unselected terminals, undeclared suffix flags, alternatives, numeric/text/pattern bounds, NUL rejection, overlapping positive rules, malformed fields and size/depth boundaries. Matching does not interpret a shell command or infer application-level authority.

`native/ward/src/host_job.rs` supplies the broker's host-job primitive. It requires the existing controller's verified resource-limited service, checks selected command terminals before launch, snapshots up to 64 MiB of executable bytes, and compares their SHA-256 with the selected executable. The declared absolute path may be an installed symlink alias; resolution must reach a regular executable accessible to the caller. The declared name remains `argv[0]`, preserving alias-selected modes. Execution uses the sealed copy through its descriptor; changed installed bytes, including a symlink retargeted to different bytes, require a new selection. This binds the main executable, not its interpreter, shared libraries, configuration or child executables. A shebang interpreter receives the descriptor path as its script filename, so a script must not rely on `$0` naming its original installation directory.

Jobs retain host filesystem, network and user/group namespaces, no new privileges, fixed `/` working directory and EOF stdin. The former private user/PID namespace prevented real host tools from referring to unmapped host user IDs. Each job now occupies a delegated child cgroup under the controller's aggregate resource ceilings. A small forked guardian observes owner and target pidfds, kills the job group on completion or owner death, and removes the group after a bounded kernel empty-group event wait. Normal completion and cancellation report incomplete cleanup as an error; the destructor has only a one-shot fallback, not sleep/retry cleanup. Only standard host home/XDG/session/locale variables are inherited, with a fixed `/usr/bin` PATH; no provider-specific lookup or worker-supplied environment is involved. Custom CLI environment variables and input streams remain unsupported. Output is binary-safe and limited to 2 MiB independently for stdout and stderr, drained nonblocking with a bounded per-poll budget. The default ten-second job deadline includes preparation; synchronous executable reads additionally depend on the controller's existing watchdog for stalled I/O. Jobs do not create separately budgeted services.

The real supervised fixture verifies literal arguments (including spaces, an empty argument and shell-looking text), output and exit status, standard environment/cwd, no leaked descriptors and no-new-privileges, captured executable bytes surviving a later source edit, rejection of a subsequent call using the old digest, and both output limits. A double-forked, detached descendant is observed through a kernel pidfd and exits after cancellation, dropping the job, normal command exit, timeout and abrupt job-owner exit without destructors. The parent controller remains alive during these checks. These establish job mechanics, not broker admission, review/approval/revocation integration, authenticated gh behavior or containment of effects delegated to other host services.

An exec request may explicitly declare `lifetime: "plugin"`. The review and signed grant bind that choice along with its executable and leaves; omitted/default `request` lifetimes retain their existing serialization and ten-second limit. Plugin-lifetime foreground jobs and their forwarding helpers have no execution deadline, but preparation, output size, two-job concurrency and controller resource ceilings stay bounded. Closing the forwarding connection cancels its job, as do plugin stop/revocation and owner death. A command's normal exit still terminates its descendants; this is not detached background authority. Generic supervised tests exercise a job beyond ten seconds, a real bootstrap caller beyond its former twelve-second reply timeout, caller cancellation and long-job revocation. No concrete plugin is embedded in these tests.

Environment, working directory, stdin and inherited descriptors are additional inputs, not an implicit worker-controlled escape hatch. Host execution can delegate network, account and filesystem authority even when those resources are absent from the worker. Matching a command grammar does not prove read-only application semantics. In particular, an unrestricted API body or a shell-capable subcommand remains broad authority. Command-tree matching also does not mediate the CLI's own descendant executions; process supervision and revocation must not be described as descendant executable filtering.

Supervised-worker integration tests additionally cover broker denial, selected and unselected leaves, literal response transport, bounded I/O, busy rejection, deadlines and revocation. The broker permits two concurrent exec jobs and at most 32 exec admissions per second, within the shared admission ceiling. A forwarding caller retries only replies that explicitly mean no job started, for up to 120 seconds; it never retries a failed job or lost reply that could duplicate a mutation. Dispatch returns after one launch attempt so executable verification does not batch across the controller's watchdog renewal and owned-job polling.

The GitHub fork's abandoned HTTP/account adapter has been replaced with explicit `/bootstrap --exec gh` calls in the original helper and a manifest declaring eleven executable leaves. There is no `gh` shim or PATH override. Its original helper retains GraphQL documents, pagination, aggregation, filters and notification-boundary behavior. A private integration fixture runs that helper inside the actual worker and `/usr/bin/gh` in host jobs, using only a fake credential file and a local Unix HTTP API. An additional empty network namespace prevents all Internet access. Six ten-case runs passed before replacing the forwarding shim: ordinary access, read-only selection, declined sign-in, logged-out credentials, partial-result errors and rate limiting. After switching to explicit bootstrap calls, the ordinary, read-only and declined-sign-in runs passed again. They verify paginated notifications, repositories and Actions, owned/organization/archive/fork filtering, authored PR check rollups, Off/Recent/All scans, repository/failure limits, and exact single/bulk notification writes. Declining write leaves produces no API writes; declining sign-in produces no API calls. Token-output flags, arbitrary GraphQL and foreign URLs are denied. No real credentials were read or real inbox threads changed. These are helper/transport results, not completed original-panel or real-desktop acceptance.

The Omagotchi port declares optional notifications, private storage, exact package-query leaves and one `pw-play` exec leaf restricted to volume plus sixteen exact staged sound files. Its original sound and notification functions use explicit bootstrap calls; no app-specific host adapter is added. The maintained storage integration test proves saved bytes across four real supervised worker/controller lifetimes, including an ungranted ephemeral home and regrant access to retained data. Separate concrete-plugin experiments now verify original Feed/save/restart recovery, both package observations and the Feed sound on a private PipeWire server: granted playback produces nonzero samples from the staged sound; declining sound produces no stream or nonzero samples while Feed still saves. Full sound-event coverage, real-speaker output, notifications from this port and roaming geometry remain unverified or unfinished. Storage selection is exposed in the CLI and reviewer. The maintained private-display reviewer test verifies pointer selection on/off, exact saved approval, activation, reopening with an unselected draft and retained grants, and revocation; selected, denied and enabled captures were visually inspected. Integration exposed an obsolete private-home IPC assumption: bootstrap now permits private directory sockets only under temporary and runtime roots, never persistent home. The disk-backed storage test rejects a host socket placed in saved data while proving restart/regrant persistence.

Use focused automated tests and real Quickshell private-display verification. Do not manipulate the active desktop, account stores, pet state or hardware during preparation. The broader deferred security/release program and the final authorized real-desktop demonstration remain separate gates.

## Delegation checkpoint

The required/optional schema, typed read/write directory grants, admitted-grant snapshot, and publication-size preflight are implemented. Prototype compatibility readers have been removed rather than carried into the new contract. The root agent integrated CLI/reviewer selection and own-panel lifecycle and independently verified ordinary worker isolation and a writable-folder GUI flow. This is incremental evidence, not completion of the inventory above; original-plugin persistence, real-account GitHub acceptance, playback/device integrations and final desktop demonstration remain open.

The handed-off runtime/grant work has been absorbed into this branch and independently tested. GitHub and Omagotchi ports are committed to draft PRs against the user's fork base branches only: [GitHub #3](https://github.com/jacob-vincent-mink/omarchy-github/pull/3) and [Omagotchi #3](https://github.com/jacob-vincent-mink/omagotchi/pull/3). No original plugin repository receives writes.

Before the handoff, the URL-related Rust unit suite passed all 39 tests, and the four notification-suite entry points passed with both systemd and graphics gates enabled. Actual isolated child cases include URL denial, both launch modes, all three broker grants together, invalid input/descriptors, cross-alias denial, busy/rate/timeout behavior and in-flight revocation. These are private-recorder results, not completed original GitHub browser behavior or a newly staged shared-runtime proof. The browser launcher's exact-flag regression test also passed.

An independent uncommitted probe subsequently invoked a byte-identical snapshot of the actual URL host helper through a one-second caller timeout and private recorder-only launchers. Both browser and webapp modes acknowledged in under 20 ms in this run, preserved the exact URL as one argument, and completed a 1.5-second recorder task in a separate transient service after the caller returned. Invalid modes and argument counts failed. This establishes launch acceptance and process-lifetime separation for that helper snapshot, not actual browser display, authorization by the broker, or original-plugin navigation. No real browser, account or desktop configuration was used.
