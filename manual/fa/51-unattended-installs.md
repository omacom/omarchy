# نصب‌های بدون ناظر

ISO مربوط به Omarchy می‌تواند بدون حضور هیچ‌کس پشت صفحه‌کلید، خودش را نصب کند. اگر برنامهٔ نصب‌کننده درایو دومی با برچسب `cidata` پیدا کند که فایل‌های پیکربندی‌اش را حمل می‌کند، آن‌ها را کپی می‌کند، جادوگر راه‌اندازی را به‌طور کامل رد می‌کند، و به‌تنهایی دوباره راه‌اندازی می‌شود و وارد سیستم نهایی می‌شود. نه ساخت خاصی از ISO لازم است، نه یک ورودی اضافی در منوی بوت — اگر چنین درایوی متصل نباشد، هیچ چیز تغییر نمی‌کند و همان جادوگر معمولی را می‌بینید.

این ویژگی Omarchy را به گزینه‌ای عالی به‌عنوان ایمیج پایه برای محیط‌های توسعهٔ یک‌بارمصرف تبدیل می‌کند: یک VM در Proxmox یا با Packer بسازید، آن را بوت کنید، رهایش کنید و بروید، و با SSH وارد شوید. `cidata` همان برچسب `NoCloud` در cloud-init است، پس همهٔ ابزارهای رایج مجازی‌سازی از قبل می‌دانند چطور چنین درایوی را متصل کنند.

## فایل‌های پیکربندی

این فایل‌ها دقیقاً همان چیزهایی هستند که جادوگر خود برنامهٔ نصب‌کننده می‌نویسد، پس ساده‌ترین راه برای به دست آوردن یک مجموعهٔ اولیه این است که یک نصب تعاملی (مثلاً در یک VM) انجام دهید و آنچه را که در `/root` نوشته است کپی کنید:

| File | Required | Purpose |
|------|----------|---------|
| `user_configuration.json` | بله | دیسک، نام میزبان، منطقهٔ زمانی، صفحه‌کلید |
| `user_credentials.json` | بله | نام کاربری و هش گذرواژه، و عبارت عبور LUKS برای یک نصب رمزگذاری‌شده |
| `user_encrypt_installation.txt` | نه | وقتی پیکربندی یک بلوک `disk_encryption` دارد، `true` است |
| `authorized_keys` | نه | کلیدهای عمومی SSH، هر کدام در یک خط |
| `tailscale_authkey` | نه | کلید احراز هویت Tailscale برای پیوستن به tailnet شما در اولین بوت |

هش گذرواژه برای `user_credentials.json` را با `openssl passwd -6 "yourpassword"` بسازید.

نام و ایمیل برای کامیت‌های git جزئی از نصب نیستند. وقتی دستگاه بالا آمد آن‌ها را تنظیم کنید، برای مثال از طریق SSH، با `omarchy setup git --name "Jane Doe" --email jane@example.com`.

همچنین می‌توانید به جای `user_credentials.json` یک فایل خالی با نام `defer-provisioning` قرار دهید. این کار همان [نصب آماده‌سازی برای مالک دیگر](02-getting-started.md) را اجرا می‌کند که می‌توانید به‌صورت تعاملی فعالش کنید: دستگاه بدون هیچ جزئیات شخصی نصب می‌شود، و هر کس اول آن را بوت کند صفحه‌کلیدش را انتخاب می‌کند و کاربرش را می‌سازد. این حالت برای دستگاه‌های ایمیج‌گیری است، جایی که درایو اصلاً نباید حامل اطلاعات ورود هیچ‌کس باشد.

## دسترسی SSH

وقتی `authorized_keys` وجود دارد، برنامهٔ نصب کلیدها را به‌عنوان `~/.ssh/authorized_keys` کاربر تنظیم می‌کند، `sshd` را فعال می‌کند و فایروال را برای آن باز می‌کند. (یک نصب استاندارد Omarchy، openssh را با سرویس غیرفعال و پورت بسته ارائه می‌دهد، پس یک دستگاه بدون ناظر در غیر این صورت غیرقابل دسترس می‌بود.) برنامهٔ نصب فقط کلیدهای شما را اضافه می‌کند — هیچ‌یک از تنظیمات احراز هویت دیگر دیمن SSH را سست نمی‌کند.

وقتی `tailscale_authkey` وجود دارد، دستگاه در عوض در اولین بوت به tailnet شما می‌پیوندد: Tailscale از بسته‌های همراه ISO نصب می‌شود، فایروال به رابط tailnet اجازه می‌دهد، و یک کار پس‌زمینه به محض اینکه دستگاه واقعاً شبکه داشته باشد، پیوستن را اجرا می‌کند و تا موفقیت آن را دوباره تلاش می‌کند. از یک کلید قابل استفادهٔ مجدد و از پیش تأییدشده استفاده کنید تا یک ایمیج درایو بتواند به دستگاه‌های زیادی خدمت دهد.

## ساخت درایو cidata

هر فایل‌سیستمی با برچسب درست کار می‌کند. یک ISO کوچک راه آسان است:

```bash
mkdir cidata
cp user_configuration.json user_credentials.json authorized_keys cidata/
genisoimage -output cidata.iso -volid cidata -joliet -rock cidata/
```

سپس آن را در کنار ISO مربوط به Omarchy به VM متصل کنید. این یک مثال کامل Proxmox است:

```bash
qm create 101 --name my-omarchy \
  --bios ovmf --machine q35 --cpu host --cores 4 --memory 8192 \
  --ostype l26 --scsihw virtio-scsi-single \
  --efidisk0 local-lvm:0,efitype=4m,pre-enrolled-keys=0 \
  --scsi0 local-lvm:40,discard=on,iothread=1 \
  --net0 virtio,bridge=vmbr0 --vga virtio --serial0 socket \
  --ide2 local:iso/omarchy.iso,media=cdrom \
  --ide3 local:iso/cidata.iso,media=cdrom \
  --boot order='scsi0;ide2'

qm start 101
```

ترتیب بوت عمداً دیسک را اول فهرست می‌کند: دیسک خالی در اولین بوت به ISO می‌رسد، و سیستم نصب‌شده از آن به بعد همیشه از دیسک بوت می‌شود.

## دو هشدار

نصب‌های رمزگذاری‌شدهٔ بدون ناظر کاملاً بدون ناظر نیستند — هنوز کسی باید در اولین بوت عبارت عبور LUKS را تایپ کند. و آن عبارت عبور در سطح بالای `user_credentials.json` به‌عنوان `encryption_password` قرار می‌گیرد — archinstall آن را از آنجا می‌خواند، نه از بلوک `disk_encryption` در `user_configuration.json` — پس با یک درایو cidata ساخته‌شده از یک نصب رمزگذاری‌شده مثل رازی که هست رفتار کنید.
