# তদারকিবিহীন ইনস্টল

Omarchy ISO কীবোর্ডের সামনে কেউ না থাকলেও নিজে নিজেই ইনস্টল হতে পারে। ইনস্টলার যদি `cidata` লেবেলযুক্ত একটি দ্বিতীয় ড্রাইভ পায় যাতে এর কনফিগারেশন ফাইলগুলো আছে, তাহলে এটি সেগুলো কপি করে নেয়, সেটআপ উইজার্ড পুরোপুরি এড়িয়ে যায়, এবং নিজে নিজেই সম্পূর্ণ সিস্টেমে রিবুট করে। কোনো বিশেষ ISO বিল্ড নয়, কোনো বাড়তি বুট মেনু এন্ট্রি নয় — এমন কোনো ড্রাইভ সংযুক্ত না থাকলে, কিছুই বদলায় না এবং আপনি স্বাভাবিক উইজার্ডই পান।

এটি Omarchy-কে ফেলে দেওয়া যায় এমন dev এনভায়রনমেন্টের বেস ইমেজ হিসেবে দারুণ করে তোলে: Proxmox-এ বা Packer দিয়ে একটি VM তৈরি করুন, বুট করুন, চলে যান, SSH দিয়ে ঢুকুন। `cidata` হলো cloud-init `NoCloud` লেবেল, তাই সব সাধারণ virtualization টুলিং ইতিমধ্যেই জানে কীভাবে এমন একটি ড্রাইভ সংযুক্ত করতে হয়।

## কনফিগারেশন ফাইলগুলো

ফাইলগুলো ঠিক তাই যা ইনস্টলারের নিজের উইজার্ড লেখে, তাই একটি শুরুর সেট পাওয়ার সবচেয়ে সহজ উপায় হলো একটি ইন্টারঅ্যাক্টিভ ইনস্টল চালানো (ধরুন, একটি VM-এ) এবং এটি `/root`-এ যা লিখেছে তা কপি করা:

| ফাইল | আবশ্যক | উদ্দেশ্য |
|------|----------|---------|
| `user_configuration.json` | হ্যাঁ | ডিস্ক, হোস্টনেম, টাইমজোন, কীবোর্ড |
| `user_credentials.json` | হ্যাঁ | ব্যবহারকারীর নাম ও পাসওয়ার্ডের হ্যাশ, আর একটি এনক্রিপ্ট করা ইনস্টলের জন্য LUKS পাসফ্রেজ |
| `user_encrypt_installation.txt` | না | কনফিগারেশনে একটি `disk_encryption` ব্লক থাকলে `true` |
| `authorized_keys` | না | SSH পাবলিক কী, লাইনপ্রতি একটি |
| `tailscale_authkey` | না | প্রথম বুটে আপনার tailnet-এ যোগ দেওয়ার জন্য Tailscale auth key |

`user_credentials.json`-এর জন্য পাসওয়ার্ড হ্যাশ তৈরি করুন `openssl passwd -6 "yourpassword"` দিয়ে।

git কমিটের জন্য নাম ও ইমেল ইনস্টলের অংশ নয়। মেশিন চালু হয়ে গেলে সেগুলো সেট করুন, যেমন SSH দিয়ে, `omarchy setup git --name "Jane Doe" --email jane@example.com` দিয়ে।

আপনি `user_credentials.json`-এর বদলে `defer-provisioning` নামে একটি খালি ফাইলও রেখে দিতে পারেন। এটি সেই একই [অন্য মালিকের জন্য প্রস্তুত করার ইনস্টল](02-getting-started.md) চালায় যা আপনি ইন্টারঅ্যাক্টিভভাবেও চালু করতে পারেন: মেশিনটি কোনো ব্যক্তিগত বিবরণ ছাড়াই ইনস্টল হয়, এবং যিনি এটি প্রথমবার বুট করবেন তিনি তার কীবোর্ড বেছে নেন এবং তার ব্যবহারকারী তৈরি করেন। ইমেজিং রিগের জন্য এটাই সেই মোড, যেখানে ড্রাইভে কারোরই ক্রেডেনশিয়াল থাকা উচিত নয়।

## SSH অ্যাক্সেস

যখন `authorized_keys` থাকে, তখন ইনস্টল কীগুলোকে ব্যবহারকারীর `~/.ssh/authorized_keys` হিসেবে সেট আপ করে, `sshd` সক্রিয় করে, এবং এর জন্য ফায়ারওয়াল খুলে দেয়। (একটি স্টক Omarchy ইনস্টলে openssh থাকে সার্ভিস নিষ্ক্রিয় এবং পোর্ট বন্ধ অবস্থায়, তাই একটি তদারকিবিহীন মেশিন অন্যথায় অপ্রাপ্য হয়ে থাকত।) ইনস্টল শুধু আপনার কীগুলোই যোগ করে — এটি SSH ডিমনের অন্য কোনো অথেনটিকেশন সেটিং শিথিল করে না।

যখন `tailscale_authkey` থাকে, তখন মেশিনটি এর বদলে প্রথম বুটে আপনার tailnet-এ যোগ দেয়: Tailscale ISO-র বান্ডল করা প্যাকেজগুলো থেকে ইনস্টল হয়, ফায়ারওয়াল tailnet ইন্টারফেসকে অনুমতি দেয়, এবং একটি ব্যাকগ্রাউন্ড জব মেশিনে আসলেই নেটওয়ার্ক আসামাত্রই যোগ দেওয়ার কাজটি চালায়, সফল না হওয়া পর্যন্ত বারবার চেষ্টা করে। একটি পুনরায় ব্যবহারযোগ্য, আগে থেকে অনুমোদিত কী ব্যবহার করুন যাতে একটি ড্রাইভ ইমেজ অনেকগুলো মেশিনে কাজ করতে পারে।

## cidata ড্রাইভ তৈরি করা

সঠিক লেবেলযুক্ত যেকোনো ফাইলসিস্টেমই কাজ করবে। একটি ছোট্ট ISO-ই সহজ উপায়:

```bash
mkdir cidata
cp user_configuration.json user_credentials.json authorized_keys cidata/
genisoimage -output cidata.iso -volid cidata -joliet -rock cidata/
```

তারপর এটি Omarchy ISO-র পাশাপাশি VM-এর সঙ্গে সংযুক্ত করুন। এখানে একটি সম্পূর্ণ Proxmox উদাহরণ দেওয়া হলো:

```bash
qm create 101 --name my-omarchy \
  --bios ovmf --machine q35 --cpu host --cores 4 --memory 8192 \
  --ostype l26 --scsihw virtio-scsi-single \
  --efidisk0 local-lvm:0,efitype=4m,pre-enrolled-keys=0 \
  --scsi0 local-lvm:40,discard=on,iothread=1 \
  --net0 virtio,bridge=vmbr0 --vga virtio --serial0 socket \
  --ide2 local:iso/omarchy.iso,media=cdrom \
  --ide3 local:iso/cidata.iso,media=cdrom \
  --boot order='scsi0;ide2'

qm start 101
```

বুট অর্ডারে ইচ্ছে করেই ডিস্ককে প্রথমে রাখা হয়েছে: খালি ডিস্কটি প্রথম বুটে ISO-তে চলে যায়, এবং এরপর থেকে ইনস্টল করা সিস্টেম সবসময় ডিস্ক থেকে বুট হয়।

## দুটি সতর্কতা

এনক্রিপ্ট করা তদারকিবিহীন ইনস্টল পুরোপুরি তদারকিবিহীন নয় — প্রথম বুটে কাউকে এখনো LUKS পাসফ্রেজ টাইপ করতে হয়। এবং সেই পাসফ্রেজটি `user_credentials.json`-এর শীর্ষ স্তরে `encryption_password` হিসেবে যায় — archinstall এটি সেখান থেকেই পড়ে, `user_configuration.json`-এর `disk_encryption` ব্লক থেকে নয় — তাই একটি এনক্রিপ্ট করা ইনস্টল থেকে তৈরি একটি cidata ড্রাইভকে সেই গোপন জিনিস হিসেবেই বিবেচনা করুন যা এটি আসলে।
