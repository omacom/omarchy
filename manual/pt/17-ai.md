# IA

Executa um comando para instalar a respetiva CLI na primeira utilização e, depois, autentica-te quando te for pedido. O Hermes e o OpenClaw são as exceções: nada é instalado para eles através do mise, e escolher qualquer um deles configura a sua própria cópia com atualização automática, como a secção de aplicações de ambiente de trabalho abaixo explica.

### Instalar e atualizar agentes

Exceto o Hermes e o OpenClaw, estes agentes utilizam a instalação lazy do mise: o primeiro arranque instala a CLI, e os arranques posteriores reutilizam-na. O mise também verifica se existe uma nova versão de um agente instalado, no máximo uma vez de quatro em quatro horas, mesmo antes de ele arrancar ou em segundo plano num prompt da shell. Se essa atualização falhar ou estiveres offline, a versão instalada é a que funciona. O `omarchy update` atualiza os agentes instalados com o resto do Omarchy, e o `mup` atualiza apenas as ferramentas geridas pelo mise.

Um atualizador próprio de um agente, como `claude update`, `codex update` ou um botão de atualização numa aplicação, não atualiza a instalação gerida pelo mise. O `codex update` falha, e o `claude update` pode comunicar sucesso ao instalar uma cópia separada que o mise não acompanha. Se preferires utilizar o instalador e o atualizador nativos de um agente, adiciona-o a `disable_tools`; consulta [Ferramentas CLI pré-instaladas](18-development-tools.md#preinstalled-cli-tools).

Para instalares todas as ferramentas lazy configuradas antes de precisares delas, executa `mise install --include-lazy`. Isto inclui as outras ferramentas CLI predefinidas do Omarchy, bem como os agentes. Consulta [Ferramentas CLI pré-instaladas](18-development-tools.md#preinstalled-cli-tools) para instalares uma única ferramenta ou utilizares a tua própria instalação.

O `grok` é instalado através do pacote first-party `grok` do mise, da mesma forma que o `claude` e o `codex`. Executa `grok`, ou escolhe-o em _Agent > Harness_. Ignora o instalador `curl | bash` em x.ai. Esse caminho coloca uma segunda cópia em `~/.grok/bin`, coloca-a no início do `PATH` e substitui o wrapper do Omarchy.

O `dsh` abre a sua interface de browser em `127.0.0.1:3080`, com o diretório de arranque como o seu espaço de trabalho predefinido. A sua interface de browser não aceita um prompt inicial, por isso `omarchy agent prompt` abre-o com o prompt na tua área de transferência para colares. O Omarchy arranca-o com o preset de permissão sem aprovação da DeepSeek. O DeepSeek Harness envia registos de sessão para a DeepSeek quando utilizas a sua API de modelo oficial; desativa isso em _Settings > General > Upload Session Log_ na sua interface de browser. O feedback que lhe enviares também é enviado com a sessão, a menos que o arranques com `DSH_TELEMETRY_MODE=DISABLED`.

### O agente predefinido

Escolhe o teu agente predefinido com `omarchy default agent <name>` ou em _Agent > Harness_ no Omarchy Menu (`Super + Space`). Se o agente ainda não estiver instalado, o facto de o escolheres instala-o primeiro, e ele também ganha um lançador próprio no lançador de aplicações, ao lado de Agent. Um Omarchy acabado de instalar vai convidar-te a fazer esta escolha com uma notificação única.

Escolher o Claude também tenta configurar a sua extensão de browser para Chromium, Chrome, Brave, Brave Origin e Edge. A configuração da extensão aplica-se a todos os utilizadores e pode pedir-te a palavra-passe do sistema; cancelar ou uma instalação da extensão que falhe continua a selecionar e a arrancar o Claude. Reinicia o browser, ativa a extensão se te for pedido e inicia sessão no Claude para terminar a ligação. Executa `/chrome` no Claude para verificar a ligação. O Firefox e o Zen não suportam esta extensão. Se o Claude já era o teu predefinido antes de esta configuração ser adicionada, seleciona-o novamente para instalar a extensão.

Depois de escolheres, `Super + Shift + Ctrl + A` arranca o agente predefinido numa janela de terminal dedicada (ou abre o seletor se ainda não tiveres escolhido). Também podes arrancá-lo diretamente para uma tarefa com `omarchy agent prompt "Review this project"`. O Freebuff e o DeepSeek Harness não aceitam um prompt inicial, por isso abrem com o prompt na tua área de transferência para colares. Os agentes arrancados desta forma funcionam sem supervisão nos respetivos modos de não parar para perguntar, por isso prepara-te para eles fazerem mesmo coisas! O MiniMax Code não tem um modo desses para as suas sessões interativas, por isso pede permissões como habitualmente. E como os agentes se recusam a memorizar a confiança para o teu diretório pessoal, os arranques a partir de `$HOME` começam antes em `~/Work`.

Também existem atalhos de terminal: `a` executa o agente predefinido no terminal atual, enquanto `c`, `cx` e `cy` arrancam o OpenCode, o Claude Code e o Codex diretamente (também nos seus modos de aprovação automática). As mudanças de tema também se sincronizam com os agentes: Claude Code, Pi, OpenCode e Hermes (depois de o Omarchy o ter instalado) acompanham-te todos quando mudas o tema do Omarchy.

### As instruções do teu agente

As regras pessoais para cada agente vão para `~/.agents/AGENTS.md`, ao lado das skills partilhadas em `~/.agents/skills`. Abre-o em _Agent > Instructions_, que também o liga a cada harness que mantém o seu próprio ficheiro global: `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.pi/agent/AGENTS.md`, `~/.config/opencode/AGENTS.md`, o `~/.copilot/copilot-instructions.md` do Copilot, e assim por diante. O Crush e o Amp leem a ligação `~/.config/AGENTS.md`, enquanto o omp, o Kimi e o DeepSeek Harness leem `~/.agents/AGENTS.md` diretamente. Escolher um agente predefinido também o liga. Um ficheiro de instruções que já tinhas torna-se o partilhado se ainda não existia nenhum; caso contrário, é mantido ao lado da ligação como `.bak`. Executa `omarchy agent instructions` para voltar a ligar depois de instalares outro agente.

### O painel de agentes

A barra superior tem um ícone de agentes. Antes de teres configurado um agente, o seu painel guia-te ao iniciar sessão no Claude, no Codex ou no Grok, e o primeiro torna-se o teu agente predefinido. Depois disso, o painel coloca cada subscrição numa só página: cada agente e conta com o seu plano, um medidor para cada um dos seus limites de sessão de 5 horas e semanais com o tempo até ser reposto (passa o rato por cima para veres a percentagem exata), ou o saldo pré-pago restante, sob uma linha que roda pelo que utilizaste em todos eles, como tokens esta semana e o teu modelo mais utilizado. Em _Make something cool_, oferece prompts iniciais para um novo tema, plugin, aplicação ou jogo que entregam a tarefa ao teu agente predefinido. As aplicações são construídas da forma como as próprias Hype, Monologue e Omacut do Omarchy são, em C++ e Qt Quick, a seguir a skill de agente omarchy-make-app, e o compilador e as peças Qt de que precisam vêm instalados. Os jogos são uma única página three.js em `~/Games/vibes`, a seguir a skill de agente omarchy-make-game, e todos abrem a partir de um único lançador Game Vibes no tema atual; carregam o three.js a partir da web, por isso precisam de uma ligação para arrancar. Claude Code, Codex, Grok, Kimi, Cursor e a sua franquia Grok Bot, GitHub Copilot, Muse, Antigravity e Devin estão abrangidos de fábrica com os seus limites, o Kimchi com o seu plano, créditos pré-pagos e orçamentos de despesa, e Hermes, Mistral Vibe e Qwen Code mostram as suas sessões e tokens depois de os teres utilizado. Os planos de fornecedores e as chaves que utilizas através de pi, omp ou opencode também aparecem: OpenCode Zen e Go, o Z.ai GLM Coding Plan, Ollama Cloud, o MiniMax Token Plan e Synthetic com os seus limites; OpenRouter e DeepSeek com os seus saldos pré-pagos; Fireworks com a sua despesa nos últimos 30 dias. Os tokens de modelos que executas no teu próprio hardware também contam para os totais; os próprios modelos têm um painel próprio, descrito em [Modelos locais](#local-models). Cada agente é contado uma vez, sob quem o fatura, por mais harnesses que utilizes para o usar.

Clica com o botão esquerdo no ícone da barra ou prime `Super + Ctrl + X` para o painel, clica com o botão direito para arrancar o teu agente predefinido e clica com o botão do meio para atualizar. Os registos de utilização por trás dele são regenerados de 15 em 15 minutos por `omarchy agent usage update`, e o painel pode até fundir a utilização das tuas outras máquinas através de uma pasta sincronizada. Consulta o README em `$OMARCHY_PATH/shell/plugins/agents/` para as definições completas.

### Várias subscrições

Se pagares por mais do que um plano Claude, Codex ou Grok — um Max pessoal e um de trabalho, por exemplo — o Omarchy pode manter todos com sessão iniciada e mover-se entre eles. Adiciona uma subscrição com o + no painel de agentes, que te guia ali mesmo, ou com `omarchy agent account add claude Work` (ou `codex`, ou `grok`). Instala a CLI se ela estiver em falta. A primeira conta de um fornecedor inicia sessão através do teu browser normal, exatamente onde a CLI sempre procura. Todas as seguintes iniciam sessão através de uma janela privada, para que a conta em que o teu browser já tem sessão iniciada não seja apanhada por engano; inicia sessão aí como a conta que estás a adicionar, e fecha primeiro qualquer janela privada que já tenhas aberta. Nunca termines a sessão na CLI para fazer isto: terminar a sessão revoga o início de sessão guardado, e essa conta teria de ser adicionada novamente.

Para copiares os inícios de sessão das tuas subscrições para outra máquina Omarchy por SSH, executa `omarchy agent account copy user@laptop`. O emissor fornece um recetor temporário quando o destino não tem um instalado, para que máquinas Omarchy mais antigas possam receber contas sem uma atualização. Os recetores instalados têm precedência. Isto copia todas as subscrições Claude, Codex e Grok; adiciona nomes de fornecedores para as selecionar, como em `omarchy agent account copy laptop claude`. Os nomes das contas e os IDs de comandos correspondem à origem, a incluir contas já presentes no destino. As contas de destino não relacionadas recebem um sufixo numérico se os seus nomes entrarem em conflito, e definições, skills, plugins e histórico de conversas permanecem locais a cada máquina.

As credenciais de destino existentes são mantidas. Uma conta de origem que já tenha sessão iniciada aí tem o seu nome sincronizado sem substituir as suas credenciais; outras contas são adicionadas ao lado dela. Para substituíres credenciais guardadas de contas correspondentes, utiliza `omarchy agent account copy --replace laptop claude` depois de fechares as sessões dessa conta no destino. Um destino acabado de configurar também recebe a conta ativa e as preferências de mudança da origem; um destino já estabelecido mantém as suas.

As credenciais viajam por SSH e são guardadas em ficheiros privados no destino, por isso copia apenas para máquinas em que confias. Isto é uma cópia única, não uma sincronização contínua. Os tokens de atualização do Codex podem ser rodados por outra máquina, o que deixa um início de sessão copiado a precisar de renovação; inícios de sessão separados continuam a ser a escolha mais fiável para utilização simultânea em várias máquinas. Consulta as [orientações de autenticação de contas do Codex](https://developers.openai.com/codex/auth/ci-cd-auth).

Uma conta por fornecedor está ativa, e cada nova sessão começa como ela: `cx`, `cy`, um simples `claude`, `codex` ou `grok`, qualquer coisa arrancada através de `omarchy agent`, e scripts ou editores que encontrem a CLI no `PATH`. Muda com `omarchy agent account use work` (e volta com `omarchy agent account use main`), ou no painel ao premir o número de uma conta e depois `Enter` (ou ao clicar no seu botão Use). As sessões Claude a funcionar também mudam, a partir da sua próxima mensagem: cada sessão Claude funciona em `~/.claude`, que guarda sempre o início de sessão da conta ativa. Uma sessão Claude iniciada na pasta própria de uma conta por um Omarchy mais antigo mantém esse início de sessão até fechar, por isso a mudança nomeia essas sessões e termina sozinha quando elas desaparecerem. As sessões Codex e Grok a funcionar mantêm-se na conta com que começaram. O histórico de conversas, as definições, as skills e os plugins são partilhados entre contas, por isso `claude --continue` na mesma pasta retoma onde ficaste na nova conta.

Com mais de uma conta, o painel mostra os limites de cada conta lado a lado, com a ativa assinalada. Por predefinição, o Omarchy avisa-te quando a conta ativa ultrapassa 95% de um limite, e clicar na notificação muda para a conta com mais margem. Passa o rato sobre a linha de uma conta no painel e clica no Autoswitch que aparece ao lado de Use (ou prime `m`), ou executa `omarchy agent account mode auto`, para que ela mude sozinha; enquanto estiver ligado, o Autoswitch toma o lugar de Use, e clicar outra vez volta a avisar. Adiciona um número para mudar o limiar, como em `omarchy agent account mode auto 90`. Se todas as contas estiverem acima do limiar, serás avisado uma vez, juntamente com a indicação de qual conta fica livre primeiro. Enquanto uma conta ativa estiver a menos de 15 pontos do seu limiar (80% na predefinição), os seus limites são verificados de três em três minutos em vez de de 15 em 15.

`omarchy agent account list` mostra cada conta e os seus limites mais recentes, `omarchy agent account remove work` esquece uma, e `omarchy agent account rename primary Hey` muda o nome de uma (ou clica no nome de uma conta no painel). Estes comandos funcionam nas contas do teu agente predefinido; para chegares ao outro fornecedor, nomeia-o primeiro, como em `omarchy agent account use codex side`. O início de sessão que já tinhas em `~/.claude` ou `~/.codex` é a conta _Main_. A do Codex fica onde está; a do Claude espera numa pasta própria enquanto outra conta estiver ativa. Uma conta deixada sem utilização durante mais de cerca de oito horas pode mostrar _Sign-in required_; clica nela para iniciar sessão nessa conta outra vez diretamente no painel, ou muda para ela e inicia uma sessão, o que atualiza o início de sessão por si só. Os servidores MCP que adicionas com `claude mcp add` chegam a todas as contas Claude, uma vez que todas funcionam em `~/.claude`; para Codex e Grok, os servidores que tinhas quando uma conta foi adicionada acompanham-na, mas os posteriores só chegam à conta em que os adicionaste. O Claude Desktop mantém um início de sessão próprio, e as ferramentas Codex ou Grok configuradas com um caminho absoluto para um binário CLI não acompanham a mudança. Um `CLAUDE_CONFIG_DIR`, `CODEX_HOME` ou `GROK_HOME` explícito tem precedência sobre a conta selecionada.

### Diagnóstico de crashes

O Omarchy observa o systemd-coredump à procura de crashes de processos. Depois de escolheres um agente predefinido, qualquer programa teu que faça um core dump traz uma notificação "Process crashed" — clica nela, e o crash é entregue ao teu agente predefinido juntamente com a skill omarchy-diagnose-crash do Omarchy, que guia o agente a estabelecer os factos a partir do core dump e a decidir se o crash vale a pena ser comunicado a montante. Também podes executá-lo manualmente contra qualquer PID de `coredumpctl list` com `omarchy agent crash <pid>`.

A observação está ligada por predefinição. Desliga-a em _Trigger > Toggle > Crash Capture Off_ (ou com `omarchy toggle crash-capture`) e as notificações param; `omarchy agent crash <pid>` continua a funcionar manualmente.

Os crashes também podem ser silenciados um programa de cada vez, que é o que o diagnóstico te oferece no fim. `omarchy crash mute hyprland` para as notificações só para esse programa, `omarchy crash mute hyprland off` volta a trazê-las, e `omarchy crash mute` por si só lista o que silenciaste. Aceita o caminho do binário tão bem como o seu nome, por isso `omarchy crash mute /usr/bin/hyprland` faz o mesmo. Coloca entre aspas um nome com um espaço, como em `omarchy crash mute 'Some App'`. Tudo o resto continua a avisar, e o programa silenciado continua a falhar — isto esconde o lembrete, não corrige nada.

### Aplicações de ambiente de trabalho

O menu _Install > AI_ também inclui algumas aplicações gráficas de IA: Amp Desktop, Antigravity Desktop, a aplicação de ambiente de trabalho do ChatGPT, a aplicação de ambiente de trabalho do Claude (a beta para Linux da Anthropic, com separadores Chat, Cowork e Claude Code), Grok Bot para conversar com os modelos da xAI, Herdr Desktop, Hermes Desktop, OpenClaw, a aplicação de ambiente de trabalho do Perplexity e T3 Code. O Grok Bot é a aplicação de chat de ambiente de trabalho. O agente de programação é o comando `grok`.

O Hermes Desktop é o que deves conhecer, porque uma máquina tem um Hermes, e é o da aplicação: o Hermes só é alguma vez instalado através da aplicação, e o comando `hermes` que o agente predefinido executa é o da aplicação. Escolher o Hermes como agente predefinido instala o mesmo que a entrada _Install > AI_ instala: o pacote, e um runtime Hermes em `~/.hermes` configurado pelo próprio instalador do Hermes, o que demora alguns minutos na primeira vez. Esse runtime é o único Hermes que o comando `hermes` do terminal, o agente predefinido e a aplicação utilizam, e atualiza-se a si próprio com `hermes update` em vez de estar à espera de uma versão do Omarchy. O facto de o instalar também entrega ao Hermes o tema do Omarchy como uma skin chamada `omarchy`, que todas as superfícies do Hermes seguem à medida que mudas de tema; escolhe outra nas definições de Appearance do Hermes ou com `/skin` se preferires que ele não o faça, e o Omarchy deixa essa escolha em paz. Remover a aplicação em _Remove > AI_ fecha primeiro o Hermes, gateway incluído, leva esse runtime com ele e mantém as tuas conversas, memórias e as skills que o Hermes escreveu para si próprio, a menos que digas o contrário: pergunta, com não como predefinição, se esses dados e as tuas definições de ligação também devem ir.

A experiência de ambiente de trabalho do OpenClaw é a sua Control UI, que abre como uma aplicação web suportada pelo seu próprio gateway local. O OpenClaw vive em `~/.openclaw` e atualiza-se a si próprio: utiliza o botão "Update Gateway" da Control UI ou executa `openclaw update`, e o gateway reinicia na nova versão. O Omarchy só escolhe a versão a partir da qual uma instalação nova começa. O OpenClaw também pode ser o teu agente predefinido: escolhê-lo em _Agent > Harness_ configura essa mesma cópia em `~/.openclaw`, e o agente abre a interface de utilizador de terminal do OpenClaw ligada ao seu gateway. Remover o OpenClaw em _Remove > AI_ leva o serviço gateway e a aplicação com ele e depois pergunta se `~/.openclaw` também deve ir, uma vez que isso guarda as tuas conversas e credenciais juntamente com o próprio OpenClaw e os runtimes de plugins que ele descarrega; a predefinição mantém-no, e instalar o OpenClaw outra vez volta a apanhá-lo.

O Herdr Desktop é a aplicação de ambiente de trabalho [Herdr](https://herdr.dev): espaços, separadores e painéis de terminais e agentes de programação que continuam a funcionar no seu núcleo quando fechas a janela. Vem do próprio instalador do Herdr em vez de um pacote, por isso vive em `~/.local/share/herdr-app`, traz o seu núcleo em `~/.local/bin/herdr-core` quando ainda não tens um, e atualiza ambos por si próprio. Fica ao lado do comando `herdr` que o Omarchy inclui em `Super + Ctrl + Return` em vez de o substituir, e recebe as teclas diretas desse comando: `Alt + Return` e `Alt + Shift + Return` dividem um painel para baixo ou para a direita, `Alt + Escape` fecha-o, `Ctrl + Alt + Arrow` move entre painéis, `Alt + 1..9` e `Alt + Left/Right` escolhem um separador, e `Alt + Up/Down` movem entre espaços. `Ctrl + 1..9` escolhe um espaço e `Alt + Shift + Up/Down` percorre os agentes. As teclas de prefixo `Ctrl + Space` permanecem só para terminal, uma vez que a aplicação não consegue manter uma tecla Ctrl simples para uma sequência. O Omarchy escreve estas para `~/.config/herdr-app/keys.json`, e `omarchy-refresh-herdr-app` volta a colocá-las. O facto de o instalar escolhe o tema Omarchy do Herdr, que a partir daí segue o teu tema Omarchy. O Herdr mantém um tema para o modo claro e um para o modo escuro, por isso, depois de mudares entre um tema Omarchy escuro e um claro, escolhe Omarchy no seletor de temas do Herdr mais uma vez para o outro modo.

O T3 Code funciona a partir da sua versão oficial AppImage em `~/.local/share/t3code` em vez de a partir de um pacote, por isso atualiza-se a si próprio. O facto de o instalar pergunta se deve começar no canal Stable ou Nightly; muda mais tarde nas definições do T3 Code. Os teus tópicos e definições vivem em `~/.t3`, e remover o T3 Code em _Remove > AI_ leva-os com ele.

### Modelos locais

Executa um modelo aberto na tua própria máquina para os teus agentes de programação. Os teus prompts e código ficam na máquina; nada do que é enviado para o modelo sai dela. Começa com:

```bash
omarchy models use best text
```

Isso configura o melhor modelo de texto para esta máquina, do tipo que os teus agentes utilizam. Os modelos de imagem, vídeo e música têm um melhor próprio: `omarchy models use best image`, `video` ou `music`. Executa `omarchy models use best` para veres a escolha de cada tipo para esta máquina.

Ou abre o painel de modelos locais a partir do seu ícone de brilhos na barra superior, ao lado do ícone de agentes, ou com Super + Ctrl + Alt + X, e escolhe +. O ícone aparece quando um modelo cabe nesta máquina. O Podman, que executa os modelos, vem com o Omarchy, tal como o toolkit de contentores da NVIDIA numa máquina NVIDIA, que lhes dá a GPU; se algum estiver em falta, a primeira configuração instala-o. Depois, o Omarchy escolhe o modelo recomendado para esta máquina, descarrega-o e arranca-o. Espera uma transferência de dezenas de GB e a maior parte da memória da máquina em utilização enquanto o modelo estiver a funcionar: o Flash Next utiliza cerca de 100 GiB com o seu contexto completo de 256K. Se outros modelos ocuparem a memória de que ele precisa, é configurado parado, pronto para arrancar quando parares um. O modelo para ao terminar a sessão; para-o tu próprio quando precisares da memória para outra coisa.

`omarchy models list` mostra as opções e explica por que algumas não cabem. Para configurares outro, executa `omarchy models use <recipe>`. Hoje, `qwen3.8-flash-next-gufo` e `qwen3.8-27b-gufo` estão disponíveis para máquinas Strix Halo de 128 GB; o 27B ocupa cerca de 40 GiB, por isso deixa espaço para outro trabalho. Num portátil de 64 GB com Arc B390 da Intel, `qwen3.6-35b-a3b-llamacpp` funciona em cerca de 30 GiB. Novas receitas e recomendações chegam com `omarchy update`, através do pacote.

Cada modelo que configurares ganha a sua própria linha no painel de modelos locais: play para o arrancar, pause para o parar e libertar a sua memória, e o botão de terminal para abrir o teu agente nele. No topo, uma barra mostra como a memória da máquina está dividida entre o próprio Omarchy (o sistema e as tuas aplicações), cada modelo a funcionar, e o que está livre. Aponta para um modelo parado e a barra mostra se ele cabe, ou quanto lhe falta. Vários podem funcionar ao mesmo tempo quando cabem juntos na memória; se um não couber, o Omarchy diz qual modelo a funcionar deves parar. Arrasta linhas pelo seu logótipo para as reordenar e prime Delete numa linha selecionada para remover um modelo e a sua transferência.

Cada modelo de programação que configurares também ganha a sua própria entrada no lançador de aplicações, sob o nome do modelo e com o logótipo do seu fabricante, da forma como iniciar sessão no Claude, Codex ou Grok adiciona uma. Abre o teu agente nesse modelo e arranca o modelo primeiro se ele não estiver a funcionar: o terminal mostra-o a carregar e entrega ao agente quando estiver pronto. Remover um modelo remove a sua entrada.

Nem todos os modelos são para programação. Os modelos de imagem, vídeo e música abrem antes no Fantasi, a aplicação do Omarchy para fazer imagens, vídeo e música com um modelo a funcionar nesta máquina, escolhido lá ou a partir da sua linha no painel de modelos locais.

Um modelo continua a funcionar exatamente como foi configurado, por isso uma atualização do Omarchy nunca reinicia um sob os teus agentes. Quando o Omarchy tem um runtime mais recente ou pesos mais recentes para um modelo que tens configurado, a sua linha mostra um botão de atualização: prime-o e o modelo é configurado outra vez em segundo plano, a descarregar apenas o que mudou, e reinicia na nova versão. Um modelo que estava parado continua parado. `omarchy models update` faz o mesmo para cada modelo a partir de um terminal.

A partir da linha de comandos, `omarchy models start <recipe>` e `omarchy models stop <recipe>` fazem o mesmo, `omarchy models status` mostra cada modelo, e `omarchy agent --local` abre o teu agente predefinido no último modelo que arrancaste. pi, OpenCode e Qwen Code podem utilizar um; com qualquer outro predefinido, abre no pi, ou no OpenCode se não tiveres pi. O pi também lista cada modelo que configuraste, e os que estão em máquinas com que emparelhaste, no seu próprio seletor de modelos, por isso um simples `pi` também os alcança. Qualquer cliente compatível com OpenAI também se pode ligar: `status` mostra o endereço de cada modelo (o primeiro é `http://127.0.0.1:11435/v1`), o nome da receita é o modelo, e a chave está em `~/.config/omarchy/agent-local/key`.

`omarchy models remove <recipe>` elimina um modelo e as transferências que nenhum outro modelo utiliza.

Os runtimes de terceiros são etiquetados com o seu editor. O Omarchy executa cada modelo sem acesso à rede.

### LLM locais

O Omarchy recomenda duas formas de executar modelos LLM locais: LM Studio e Ollama. O LM Studio fornece uma interface GUI para encontrar modelos de pesos abertos, instalá-los e executá-los. É uma ótima forma de começar facilmente. O Ollama oferece uma CLI para fazer o mesmo de forma semelhante. Mas se és novo nos modelos locais, eu começaria pelo LM Studio. Podes instalar qualquer um em _Install > AI_ no Omarchy Menu.

### As skills do Omarchy

As skills de agente ajudam a IA a utilizar ferramentas específicas de uma forma específica, e o Omarchy inclui sete delas. A skill omarchy abrange adaptar o sistema, como ajustar a tua configuração do Hyprland ou regular a barra. omarchy-make-theme, omarchy-make-plugin, omarchy-make-app e omarchy-make-game abrangem fazer algo novo, omarchy-contribute abrange comunicar um bug ou enviar uma correção a montante, e omarchy-diagnose-crash trabalha através do core dump de um crash. São ligadas por symlink aos diretórios de skills do Claude Code (`~/.claude/skills`), do Codex (`~/.codex/skills`), do Pi (`~/.pi/agent/skills`), do Antigravity (`~/.gemini/config/skills`), do Hermes (`~/.hermes/skills` e cada `~/.hermes/profiles/*/skills`), e à localização genérica `~/.agents/skills`, por isso a maioria dos harnesses apanha-as automaticamente. Uma pasta de skill tua com o mesmo nome tem precedência.

Mas deves tratar estas skills como experimentais. Modelos diferentes vão utilizá-la com efeitos diferentes. É melhor executar primeiro em modo de plano, para teres uma ideia do que o agente gostaria de mudar. E depois prepara-te para reverter alterações ou até invocar `omarchy reinstall configs`, se o agente fizer uma confusão com tudo.
